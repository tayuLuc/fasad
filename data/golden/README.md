## Формат JSONL (одна строка = один пример)

```json
{"id":"g0001","text":"…","spans":[{"start_byte":87,"end_byte":127,"category":"person_name","value_source":"…"}],"split":"recall","source":"synthetic-checksum"}
```

| поле | смысл |
|---|---|
| `id` | `gNNNN`, уникален в файле |
| `text` | пример целиком, UTF-8; байты — единица отсчёта спанов (`ByteSpan`, guard-types) |
| `spans[].start_byte` / `end_byte` | `[start, end)` на границах символов; спаны не пересекаются |
| `spans[].category` | id класса (ниже); сверяется со `schema.default.json`, когда он появится |
| `spans[].value_source` | каноническое значение: для номерков — НОРМАЛИЗОВАННЫЕ цифры (ИНН 10/12, СНИЛС 11, ОГРН 13, ОГРНИП 15, PAN 15–16, IBAN без пробелов, E.164 `7XXXXXXXXXX`); для ФИО/адреса/паспорта/e-mail — строка, дословно равная фрагменту текста |
| `split` | `recall` (эталон: каждый спан обязан быть пойман) или `negative` (бэйт: ловить нельзя) |
| `source` | происхождение: `synthetic-checksum` \| `registry-example` \| `primary-invalid-vector` \| `primary-valid-vector` (golden-v1.1, валидные эталоны первички g0201–g0204) \| `doc-valid-vector` \| `foreign-bait` \| `synthetic-no-pii` |

Категории — snake_case-идентификаторы ядра совместимости SPEC §14 (в скобках —
эквивалент нейралдипа/базового слоя): `person_name` (PERSON), `inn` (INN),
`snils` (СНИЛС), `ogrn` (ОГРН), `ogrnip` (ОГРНИП), `iban`, `card_pan`
(CREDIT_CARD), `phone` (PHONE), `email` (EMAIL), `address` (адресный маркер),
`passport` (PASSPORT); в negative — `bik` (БИК), `bank_account` (BANK_ACCOUNT).
Схема категорий правится через `PUT /v1/schema` (`ClassId` — строка), поэтому
датасет не жёстко связан с enum.

## Происхождение значений (факты, не прозвук)

1. **Формулы чексумм — только таблицы `docs/dep-verify-algorithms.md`**: ИНН mod11
   (веса 2,4,10,3,5,9,4,6,8 → младшая цифра), ИНН-12 (A/B сдвиги), СНИЛС mod101
   (веса 9..1, 100/101→00, >001001998, запрет трёх подряд в теле), ОГРН-13 mod11,
   **ОГРНИП-15 mod13** (НЕ mod11), Луна по ISO/IEC 7812-1:2017 (удвоение 2-й справа,
   «Мир» = весь блок 22xxxx, не 2200–2204), IBAN mod97 (EBS204) + RU-структура
   реестра SWIFT rel.99 §2.71 (`RU2!n 9!n 5!n 15!c`, длина 33, `!c` допускает букву).
   Валидные номерки НЕ взяты из жизни — они сгенерированы по этим формулам
   детерминированным PRNG (xorshift64*, seed `0xF0D1C0DE`).
2. **Negative-невалидные номерки — дословно из таблиц эталонных векторов** первички
   (1110005080, 4234324324, 1111111111, 7743880976, 617547302703; СНИЛС
   111-111-111 11 / 151-324-910 82 / 100-222-345 67; ОГРН 9100722490217 /
   4090342700154 / 1234567890123; ОГРНИП 304500116000154 / 313242342342332;
   карты 4242424242424241 / 2200000000000005 / 1234567812345678 / 5555555555555556;
   IBAN DE89…3001 / RU03…0418 / GB82…5433; БИК 144525225, счёт 50702810900000001234).
3. **ФИО/города/организмы/адреса — вымышленные** (синтетический пул
   «Соколова Милана Фёдоровна», ОПФ+название «ООО „Ромашка“», домены `.example`);
   никаких реальных персоналий. Номера банков-контрагентов — фикстуры
   (044525225 = БИК из примера реестра SWIFT, структурно корректный).
4. Эталонные IBAN реестра (`RU03…0419`, `DE89…3000`) включены в recall как
   официальные примеры первички, это не чьи-то счета.

`data/golden/golden_gen.py` (v1, python3 stdlib). Python-тулинг разрешён рулингом
оператора 19.10 (AGENTS п.6, gutter-версия): генераторы данных — да, рантайм/сборка

(stdout — JSONL, stderr — счётчики; побайтово детерминирован). Проверка
воспроизводимости без записи в файл: `just golden-verify` — скрипт
`scripts/golden_regen_verify.py` регенит в память и сверяет SHA-256 с
B2-константой из `tests/golden_v1.rs` (единственный источник истины, копий
хэша в скриптах нет). В CI то же самое гоняет джоба `python-golden` на
ubuntu+windows (ловит и CRLF-порчу чек-аута, и дрейф генератора).
selftest внутри генератора сверяет формулы с табличными векторами первички
ДО генерации. Счётчики в README — вывод самого генератора (stderr) + пересчёт
по файлу. Rust-эквивалент `crates/guard-detectors/examples/golden_gen.rs`
остаётся отдельной задачей (SPEC §10 шаг 3); байт-инвариантность с Python-
выводом не требуется — переносится ценность (формулы + selftest), выход
проверяется гейтами того же класса.

## Правила добавления (v2 и далее)

1. Один файл = одна версия (`golden-v2.jsonl`), старые не правим — гейт
   привязан к SHA-256; при дописке пересчитываем хэш и таблицу счётчиков.
2. Каждый новый валидный номерок — по формулам первички (чек-цифра вычисляется
   генератором); каждый невалидный — табличным вектором из
   `dep-verify-algorithms.md` или явной порчей валидного с пометкой в `source`.
3. Каждая категория recall ≥ 8; negative ≈ 20–30 %; обязателен мульти-сущностный
   микс и «грязные» разрывы цифр (проверяет каскад-0 нормализатор).
4. Реальные ПДн в golden не заносятся НИКОГДА; дописка внешнего корпуса
   (`redmadrobot/pii_benchmark`, SPEC §5.6 п.6) — только после проверки, что
   разметка спанов независима от нашего каскада, и отдельным файлом.
5. Тест-гейт: `cargo test -p guard-detectors --test golden_v1`
   (парсинг, B1 count-гейт recall-класса ≥150 (KNOWN-RED на v1.0 — 146),
   B2 SHA-256, B3 UTF-8-границы/enum-ы/непересечение, B4 форматы
   `value_source`, чексуммы recall-сплита сходятся, negative-номерки не
   проходят, табличные эталоны первички воспроизводятся формулами теста) +
   `cargo test -p guard-detectors --test reference_vectors` (B5: прогон
   `reference-vectors.tsv` через `checksums::*`).

## Метрика recall (как считать)

Строгий span-match: предсказание поймано, если `[start,end)` совпадает
байт-в-байт и категория равна (для `recall`-сплита); FN = пропущенный спан,
FP = пойманный спан в `negative`-строке на месте не-PII. recall = TP/(TP+FN)
по recall-сплиту, планка ≥ 98 % при N=146+ (Wilson CI, нижняя граница ≥ 94.5 %
при 146/146; при промахе k позиций считать CI, как в §8 первички).

**Аддендум 21.10 (промер union-recall, `docs/golden-report.md`; три расхождения,
которые этот README не закрыл — правка — за владельцем файла, решение = issue):**

1. Абзац выше определяет попадание как **byte-exact**; харнес метрики
   (`crates/guard-onnx/examples/recall_golden.rs`, `tools/metrics/union_recall.py`)
   считает **byte-overlap**. На одном и том же прогоне это две разные метрики
   (числа — в golden-report §6.4). Владелец определения должен быть один;
   пока их два, «гейт закрыт» — слово с двумя значениями.
2. CI-число в абзаце устарело: промер формулой §8 даёт при n = 146 и k = n
   нижнюю границу **97.436 %**, а не 94.5 % (94.577 % соответствует n = 67).
   Число пережито ростом набора v1.0 → v1.1 и не пересчитано (issue #77).
3. «N=146+» больше не актуальный знаменатель: v1.1 = 150 recall-строк / 358
   gold-спанов (счётчики выше в §Счётчики v1). На 150 строках планка 98 %
   непроверяема ни при каком k (нужно k ≥ 151); минимальный проверяемый n по
   строкам = 189. По спанам (n = 358) планка проверяема при k ≥ 357, то есть
   **не более чем с одним промахом** (lo(357,358) = 98.4350 %, lo(356,358) =
   97.9862 % — уже нет).
4. **Дополнение 24.10 (#209-хвост): знаменатель v1.3 и пересчёт
   `k_for_bar` первичкой (формула `tools/metrics/union_recall.py::k_for_bar`,

### Рюлинг оператора 24.10 (пересмотрен указатель-канал для ВНЕШНИХ бенчей)

сборки и кода**. Для внешних **эталонных бенчей** ruling оператора 24.10: данные
тащим в git (MIT-корпус read-only метрики), указатель ненадёжен — датасет может
быть изменён/удалён, а воспроизводимость кросс-мера = часть продукта. Условия:
license-файл рядом, sha256-пин в README, snapshot/revision фиксируются,
кросс-бенч остаётся read-only мерой (не гейт recall, golden-v1 — единственный
эталон метрики, §1 не меняется).

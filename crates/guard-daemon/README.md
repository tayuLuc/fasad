# guard-daemon (`fasad`) — шаг 6

Стендэлон-демон: HTTP-фасад над каскадом 0 и обратимым хранилищем токенов.
Issue #56; контракты — SPEC §8 (HTTP-API), §3 (режимы хранилища), §1 п.6 (рамка «весь разбор завершается на 127.0.0.1»), §10 шаг 6.

Чего здесь **нет** на этом шаге (и это не баг, а границы шага):

1. исходящей сети — вообще, см. §Сеть;
2. каскадов 1+ (`X-Guard-Stage: cascade-0-only`) — см. §Деградация каскада;
3. `/v1/chat/completions`, `PUT /v1/sessions/{id}`-аутентификация, tray, `/ui` —
   шаги 7–8;
4. мьютекса «одна сессия = один пользователь»: `X-Session-ID` не аутентифицирован.

## Быстрый старт

```sh
cargo build -p guard-daemon --release
FASAD_VAULT_MODE=session FASAD_VAULT_KEY=$(openssl rand -hex 32) ./target/release/fasad
```

Баннер печатается **после** успешного бинда и показывает фактический адрес
(`FASAD_PORT=0` → репорт занятого порта, на нём держится `tests/wire_e2e.rs`):

```
fasad 0.1.0 cascade-0-only, listening on http://127.0.0.1:8765/health (классов схемы: 8, vault: session/strict, ключ: env)
```

Ключ — 32 байта из любого CSPRNG; `openssl rand -hex 32` в примере только как
самый скучный способ. В `tests/wire_e2e.rs` ключ задан литералом, чтобы CI не
зависел от шелла и от наличия `openssl` на windows-раннере.

### Переменные

| Переменная | Дефолт | Что делает |
| --- | --- | --- |
| `FASAD_BIND` | `127.0.0.1` | Только loopback. `0.0.0.0` = отказ старта, код 2 (проверено процессом: `non_loopback_bind_panics_the_test_instead_of_hanging_it`) |
| `FASAD_PORT` | `8765` | Порт; `0` = свободный, адрес в баннере |
| `FASAD_VAULT_MODE` | `stateless` | `stateless`/`3` — режим SPEC §3.3; `session`/`2` — режим §3.2 |
| `FASAD_VAULT_KEY` | нет | 64 hex-символа (32 байта). Без него ключ эфемерный: метки переживают запрос, но не перезапуск |
| `FASAD_MLOCK` | `strict` | `strict` = отказ старта при отказе `mlock`; `best_effort` = работаем без залоченной памяти. См. §Девиация #55 |
| `FASAD_SCHEMA` | встроенный канон | Путь к `schema.default.json`; содержимое сверяется с вкомпилированным байт-в-байт |
| `FASAD_TAU_LOW` / `FASAD_TAU_HIGH` | `0.20` / `0.80` | Порог экстрактора и верхняя граница уверенности |
| `FASAD_GRAY_LO` / `FASAD_GRAY_HI` | `0.22` / `0.80` | Серая зона τ_arb из #56 п.2; дефолт `τ_low` принят родителем по замеру шага 6 |
| `FASAD_MAX_BODY_BYTES` | `1048576` | Лимит тела. Перелив → 413 в нашем конверте, см. §Fail-closed |
| `FASAD_THREADS` | `8` | **Не задействован на шаге 6**: число потоков ORT понадобится каскадам 1+ |
| `FASAD_TIMEOUT_MS` | `3000` | **Не задействован на шаге 6**: таймаут наружу — шаг 7 (`X-Upstream-URL`) |

## Контракт эндпоинтов

| Метод | Путь | Тело запроса | Ответ |
| --- | --- | --- | --- |
| GET | `/health` | — | `{"version","stage","mode"}` |
| POST | `/v1/analyze` | `AnalyzeRequest` | голый массив `AnalyzedSpan[]` (форма Presidio `RecognizerResult`) |
| POST | `/v1/anonymize` | `AnonymizeRequest` | `Anonymized` |
| POST | `/v1/deanonymize` | `DeanonymizeRequest` | `Deanonymized` |
| DELETE | `/v1/sessions/{id}` | — | `{"deleted":N}` |

`405`/`404` отдаёт axum своим текстом (не наш конверт): это не ответы конвейера,
а ответы маршрутизатора, и маскировать их под конверт смысла нет.

### `POST /v1/analyze`

```jsonc
// запрос
{ "text": "…", "entities": ["inn","snils"], "score_threshold": 0.3 }
// ответ (массив!)
[{ "entity_type": "inn", "start": 27, "end": 37, "score": 1.0, "class": "inn",
   "byte_start": 49, "byte_end": 59, "role": null, "source": "checksum_rf",
   "verdict": "mask_surrogate", "validator": "inn10" }]
```

1. `entities` — фильтр классов; `score_threshold` применяется как
   `max(client, FASAD_TAU_LOW)`: поднять планку клиенту можно, опустить её ниже
   политики сервера — нет.
2. `role` всегда `null` (SPEC §14 — шаг 8).
3. `verdict` ∈ `mask_surrogate | block | audit_only`; политика из
   `X-Guard-Policy`, дефолт `mask`.

### `POST /v1/anonymize` / `POST /v1/deanonymize`

```jsonc
// запрос anonymize (режим 2, X-Session-ID: probe), spans — из /v1/analyze + имя руками
{ "text": "Ушакова Кира Саввична, ИНН 2482014338",
  "spans": [{ "entity_type": "person_name", "byte_start": 0, "byte_end": 40 },
            { "entity_type": "inn", "byte_start": 49, "byte_end": 59 }] }
// ответ (промер этой сессии)
{ "text": "Тенина Агафья Афанасьевна, ИНН [INN_1_PQLXM2SQ]",
  "items": [{ "entity_type": "person_name", "start": 0, "end": 21,
              "byte_start": 0, "byte_end": 40,
              "replacement": "Тенина Агафья Афанасьевна", "operator": "replace" },
            { "entity_type": "inn", "start": 27, "end": 37,
              "byte_start": 49, "byte_end": 59,
              "replacement": "[INN_1_PQLXM2SQ]", "operator": "mask" }] }
// deanonymize тем же текстом → { "text": "Ушакова Кира Саввична, ИНН 2482014338",
//                                "substituted": 4 }
```

1. **Оффсеты: байты — канон, символы — компатибилити.** `byte_start`/`byte_end`
   — авторитетные координаты (наш внутренний контракт, `guard-types::span`);
   `start`/`end` — те же границы исходного текста в **символах**, как у Presidio
   (первичка: `docs/dep-verify-repos.md` п.1–2 п.4 — «offsets символьные»).
   Символьные поля — входные координаты ответа, а не координаты в переписанном
   тексте: после подмены сдвиги правятся, и клиент, читающий `items[].start` как
   позицию в `text`, получил бы неверную якорь-точку. Различающий тест —
   `offsets_are_input_coordinates_not_output_ones`: при двух спанах второй
   обязан остаться на `start = 35`, тогда как координата в переписанном тексте
   уехала бы на ~100 символов вперёд (длина маркера).
2. `spans[].byte_start`/`byte_end` обязаны быть границами символов и не
   пересекаться; ошибка — `422 bad_span` / `spans пересекаются`, до первой
   подмены (полуподменённый текст наружу не уходит никогда).
3. `operator` ∈ `mask` (маркер/метка) | `replace` (суррогат ФИО).
4. `substituted` — число **замен токенов**, а не спанов: одно ФИО в режиме 2
   хранится тремя формами (фамилия/имя/отчество), поэтому промер выше даёт 4 при
   двух спанах. В режиме 3 `substituted` = числу маркеров.
4. Классы, которых нет в схеме, — `422 unknown_entity`.

## Хранилище: режимы 2 и 3

| | режим 3 `stateless` (дефолт) | режим 2 `session` |
| --- | --- | --- |
| Маркер | `[[F0#base64url]]`, AES-256-GCM, AAD = id сессии | метка `[КЛАСС_seq_nonce]` + суррогат |
| `X-Session-ID` | не нужен | обязателен (нет заголовка → `400 bad_request`) |
| Хранение на покое | ноль байт | оригиналы в moka-кэше: idle 15 мин, live 2 ч (`Limits::SPEC_DEFAULT`, `guard-vault/src/cache.rs:167-168`) |
| Обратимость | тем же процессом | тем же процессом + тем же `FASAD_VAULT_KEY` |
| `substituted` | да | да |

1. Нонс в метке (`[INN_1_IZSLOK2S]`, а не `[INN_1]`) — потому что id сессии
   придумывает клиент и он не аутентифицирован: предсказуемая метка означала бы
   подбор чужой сессии перебором. Алфавит метки — `Grammar::LABEL` (`A-Z0-9_`),
   длина ≤ 32.
2. Лимиты реестра: `MAX_SESSIONS = 256` (вытеснение FIFO через
   `engine.invalidate_session`) и `MAX_FORMS_PER_SESSION = 1024` (константа
   `config.rs`, не переменная окружения: шаг 8 меняет её правкой, а не флагом).
   Память демона не должна расти от объёма клиента, и переполнение лимита форм —
   это `422 too_many_forms` **до первой подмены**, а не тихая потеря формы:
   потерянная форма дала бы partial-restore на `/v1/deanonymize` без ошибки, то
   есть fail-open на данных. Достижимость: 1024 формы — это ~256 ФИО, а
   `FASAD_MAX_BODY_BYTES` = 1 МиБ вмещает порядка 20 000 спанов, значит лимит
   кончается раньше тела. Дубликаты внутри запроса не резервируются: 400
   вхождений одного имени = 3 формы (тест
   `duplicate_forms_within_request_do_not_reserve_twice`).
3. Суррогаты ФИО: столбец `genders` в морф-таблице у именных правил = `f,m`
   (промер 0/56), поэтому `VaultEngine::surrogat_for` на реальных ФИО из
   датасета возвращает `None` — это не дефект хранилища, а его конструкция
   (док `guard-vault::morph` отсылает шаг 6 проверять род по маске). Демон берёт
   род из окончания токена (`suffix_gender`) и вызывает
   `surrogat_for_gender`; при любом сомнении — откат на метку. Ложный род в
   документе дороже отказа маскировать: «Ушакова» → «Тенина», но никогда не
   → «Тенин».
4. `DELETE /v1/sessions/{id}` снимает и кэш оригиналов, и реестр форм; счётчик
   снятого — и в теле, и в `X-Guard-Redacted-Count`. Без `store().sync()` moka
   `iter()` не видит свежие вставки, и teardown вернул бы 0 при живой сессии.
5. Переанонимизация замазанного запрещена (P6, оба режима): спан, содержащий
   нашу метку (`[КЛАСС_СЧЁТЧИК_NONCE]`), наш токен (`[[F0#…]]`) или словоформу,
   которую хранилище этой сессии знает как суррогат, — это `422
   reanonymize_surrogate` **до первой подмены**.
   Причина не в гигиене протокола, а в ключе реверс-индекса: он устроен по
   суррогату (`guard-vault/src/lib.rs:300-303`, `StoreKey::new(session,
   "srg:" + form)`), поэтому повторная анонимизация собственного выхода
   перезатирает раннюю связь, и `deanonymize` начинает возвращать смесь чужой
   фамилии с настоящими именем и отчеством как настоящие `ПДн` (промер: три
   раунда → `200 OK` + «Ветрова Кира Саввична»). В режиме 3 тот же класс
  был тише: два раунда на одном токене давали `deanonymize` с
   `substituted: 1` и живым `[[F0#…]]` внутри «восстановленного» текста —
   partial-restore без ошибки. Проверка по любому классу, не только по
   `person_name`: дефект в ключе, а не в типе данных. Ложный отказ
   возможен, и не только на ФИО: легитимные `ПДн` могут совпасть по форме с
   нашей подменой (пароль `[AB_12]`, фамилия, совпавшая сгенерированной).
   Предпочтение отдано ложному отказу: тихая подмена данных неотличима от
   правды, а `422` клиент видит и разберётся сам. Корневая правка (ключ с
   оригиналом, отказ на неоднозначном развороте) — вне шага 6, заводится
   отдельной задачей на шаг 7.

## Девиация #55: `mlock` (задокументирована, а не замолчана)

`#55` (контракт залоченной памяти) **не подписан**. Реализация `guard-vault`
ложит буферы через `mlock(2)`/`VirtualLock`, и мы не утверждаем наружу, что
память не свопится, ни на одной платформе: исход `mlock` при исчерпании лимита
платформозависим, а промера «гарантия на macOS» у нас нет. Что промерено в этой
сессии — так это то, что `strict`-старт на macOS-arm64 проходит (баннер
`vault: stateless/strict`), а отказ залочки у нас не молчание, а явная политика.

Что делает демон:

1. `FASAD_MLOCK=strict` (дефолт) — при отказе `mlock` **старт не состоится**
   (код 2, причина в stderr). Молча залочить «столько, сколько дали» = соврать.
2. `FASAD_MLOCK=best_effort` — работаем без залочки; в баннере это видно
   (`vault: session/best_effort`), т.е. деградация наружу, а не внутри.
3. Целевая платформа контракта — Linux (CI-матрица ubuntu-22.04/24.04);
   macOS остаётся дев-средой, и именно поэтому девиация названа, а не «починена
   молча на одной машине».
4. Известный риск windows-раннера: `VirtualLock` там падает на квоте
   залочиваемых страниц процесса (`ERROR_NOT_ENOUGH_QUOTA` — помечено `[claim]`
   в доке `guard-vault::token::VaultError::Mlock`, промера с этого хоста нет).
   Ручка `FASAD_MLOCK=best_effort` это снимает, но в тестах и в CI мы её НЕ
   выставляем: красный windows-CI на `strict` = вопрос к контракту #55, а не
   флак, и он должен быть услышан.
5. На `X-Guard-*` отказ хранилища не маскируется: `503` с категорией, без
   имени модуля и без текста ошибки (там может быть кусок входа).

## Fail-closed: компас статусов

| Код | Когда | Тело |
| --- | --- | --- |
| `400` | `X-Guard-Policy` с непечатаемыми байтами; `X-Session-ID` вне печатаемого ASCII (`HeaderValue::to_str` отказывает и на управляющих байтах, и на 0x80-0xFF) — отдельно от «заголовка нет»: клиент, приславший мусор, не должен слышать «у вас нет заголовка»; тело не JSON; тело оборвалось битым фреймом (`bad_body`) | `{"error":{"code","message"}}` |
| `413` | тело больше `FASAD_MAX_BODY_BYTES` | `{"error":{"code":"body_too_large",…}}` — наш конверт, а не текст axum |
| `422` | класс не знает схема; спан не на границе символа; пересечение спанов; маркер не разворачивается; метка длиннее лимита; пустой оригинал; форм суррогатов больше лимита (`too_many_forms`); вход — уже замазанный нашим же механизмом, в любом режиме (`reanonymize_surrogate`) | конверт выше |
| `503` | **любой** `VaultError` (на практике `Busy` / `Mlock` / `Entropy`) **или** паника обработчика | конверт; для паники `code: internal_panic` |
| `500` | ошибка скоринга в конвейере | конверт |

1. Ни одного «успешного» ответа с частичным результатом: неразвернувшийся маркер
   = `422`, а не текст с остатком маркеров.
2. Ответ об отказе хранилища намеренно не содержит имени модуля ни в каком виде,
   только категорию.
3. Лимит тела считается по **фактически прочитанным байтам**, `Content-Length`
   не доверен; заголовок можно соврать. Ошибка потока при этом отличается от
   перелива: битый chunked даёт `400 bad_body`, а не `413`. Штатно различить
   было нечем — `is_length_limit()` в axum-core 0.5.6 нет (промер исходника
   crate), и через `to_bytes` любое исключение становилось «слишком длинно»;
   врать о причине той же ошибкой = тот же fail-open в диагностике. Тест —
   `broken_chunked_body_is_400_bad_body_not_413`.
4. Ограничен размер тела, но не время его чтения: промер этой сессии — тело из
   52 байт, накапанное по байту за 0.6 с (~24 с на запрос), получил `200 OK`
   вместо отказа. На шаге 6 это осознанный риск с потолком «только локальный
   доступ» (§1 п.6), а на шаге 7 ему место вместе с `X-Upstream-URL`: отдельная
   ручка на таймаут входящего тела, НЕ `FASAD_TIMEOUT_MS` (та названа таймаутом
   наружу, переименовывать смысл = врать об имени). Риск учтён в ревью-цикле
   PR #58 как пункт P5 и остаётся открытым до шага 7.
5. Паника обработчика перехватывается (`http::guarded`) и становится `503`, а не
   разорванным соединением; сообщение паники наружу не цитируется (в него может
   попасть вход), хук в `main.rs` печатает только `файл:строка`.
6. `Zeroizing<String>` на буферах с оригиналами: тексты всех трёх запросов и
   ответ `deanonymize`. `Anonymized.text` — обычный `String` осознанно
   (оригиналов в нём нет по построению). `Debug` на запросах печатает
   `[REDACTED]`.
7. Ни одного лог-вызова в пути запроса: ни PII, ни id сессий в stderr.

## Заголовки SPEC §8

| Заголовок | На каких ответах | Значение |
| --- | --- | --- |
| `X-Guard-Redacted-Count` | `analyze`, `anonymize`, `deanonymize`, `sessions`-DELETE | число подмен (на `analyze` — найденных спанов, на `deanonymize` — возвращённых токенов); `0` — осмысленный ноль |
| `X-Guard-Max-Risk` | `analyze` | максимальный `score` |
| `X-Guard-Latency-Ms` | все четыре POST/DELETE | миллисекунды, округление вниз |
| `X-Guard-Stage` | все успешные ответы | `cascade-0-only` на шаге 6 |
| `X-Guard-Policy` | ответ `analyze` | какая политика применена |
| `X-Guard-Threshold` | ответ `analyze` | фактически применённый порог |
| `X-Session-ID` | запрос (`session`) | id сессии: непустой, ≤ 64 байт, алфавит ASCII-буквы/цифры + `.` `_` `-` |
| `X-Upstream-URL` | — | **шаг 7**, сейчас игнорируется |

Отсутствие `X-Guard-Redacted-Count` на 2xx клиент обязан считать ошибкой:
мы никогда не подменяем счётчик нулём, если не знаем значения.

## Деградация каскада: почему `cascade-0-only`

1. `guard-onnx` наружу даёт только `arbitrate::DecideArbiter`. LockR-head
   живёт в `crates/guard-onnx/examples/recall_golden.rs` — это харнес, не
   библиотеочный API. Протаскивать его в демона = тащить пример в рантайм,
   поэтому стадия честно называется `cascade-0-only`, а не `full`.
2. Следствие для `/v1/analyze`: каскад 0 = валидаторы по цифровым классам.
   **`person_name` не находится никогда** — его ищет токен-классификатор
   (каскад 1+). Класс в схеме есть, в ответе анализа его нет; `/v1/anonymize`
   при этом маскирует имя, если спан прислан клиентом (tray-выделение, каскад
   1+ из другой сборки). Промер этой сессии: `«Ушакова Кира Саввична, ИНН
   2482014338»` → один спан `inn`.
3. Нормализатор каскада 0 не склеивает разделители внутри номера:
   `СНИЛС 65707715421` находится, `СНИЛС 657-077-154 21` — нет (issue #51).
   Это та же причина, по которой гейт #14 меряется на полном каскаде, а не на
   нулевом.
4. Метрика recall (гейт #14, ≥98 % с нижницей Вилсона) измеряется родителем на
   харнесе, не здесь; KNOWN-RED B1 остаётся `#[ignore]`.

## Сеть

Исходящих соединений у демона нет, и это не обещание «на глаз»:

1. HTTP-клиент убран из манифеста crate (он попал туда из скелета шага 3);
2. сетевой гейт дублируется тестом `tests/net_audit.rs` (манифест, скан `src/`,
   `cargo tree -i`) — он бегает в `just test` на обеих ОС; grep-рецепт
   `just net-audit` = локальное convenience (стоит в `just check`), на
   windows-ранах грепа может не быть;
3. листенер loopback — единственная сокет-операция демона: `bind`, не `connect`.

**Версия компилятора гейтов.** `rust-toolchain.toml` в репозитории нет, CI
ставит `stable` через `dtolnay/rust-toolchain` (`.github/workflows/ci.yml:30`),
т.е. версия CI = актуальный stable и может опережать локальный дефолт: промер
21.10 — CI clippy 1.99.0/1.99.1 против локального 1.97.1, и на этой разнице
`just lint` покраснел в CI, оставаясь зелёным дома (новый линт
`clippy::assert_is_empty`, 8 sites в тестах демона). Вывод, годный как
инвариант: гейт, меряемый одной локальной версией, не гейт — перед пушем
`just lint` прогоняется ещё и `rustup run <CI-версия> cargo clippy --workspace
--all-targets -- -D warnings -D clippy::unwrap_used` (промер: rc=0, плюс
ort- и decliner-строки на 1.99.1 rc=0). Пин версии в `rust-toolchain.toml` —
решение не этого шага, оно убирает саму категорию расхождения.

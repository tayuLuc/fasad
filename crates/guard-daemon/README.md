# guard-daemon (`fasad`) — шаг 6

Стендэлон-демон: HTTP-фасад над каскадом 0 и обратимым хранилищем токенов.
Issue #56; контракты — SPEC §8 (HTTP-API), §3 (режимы хранилища), §1 п.6 (рамка «весь разбор завершается на 127.0.0.1»), §10 шаг 6.

Чего здесь **нет** на этом шаге (и это не баг, а границы шага):

1. исходящей сети — вообще, см. [docs/daemon-scope.md §Сеть](../../docs/daemon-scope.md);
2. каскадов 1+ (`X-Guard-Stage: cascade-0-only`) — см. там же, §Деградация каскада;
3. `PUT /v1/sessions/{id}`-аутентификация — не аутентифицирована;
   `/v1/chat/completions` и `/ui` закрыты шагами 7c/8; tray закрыт #128
   фаза 2 (win/mac, фича `tray` — см. src/tray.rs);
4. мьютекса «одна сессия = один пользователь»: `X-Session-ID` не аутентифицирован.

## Быстрый старт

```sh
cargo build -p guard-daemon --release   # каскад-0-бинарь (харнес-контур, фича off)
FASAD_VAULT_MODE=session FASAD_VAULT_KEY=$(openssl rand -hex 32) ./target/release/fasad
```

(Продуктовый контур = сборка с `--features guard-daemon/ort-inference` +
`FASAD_MODEL_DIR`, §«Как включить монтаж» ниже: full-бинарь без весов не
стартует, #185.)

Баннер печатается **после** успешного бинда и показывает фактический адрес
(`FASAD_PORT=0` → репорт занятого порта, на нём держится `tests/wire_e2e.rs`);
второй строкой — адрес песочницы в браузере (#191, канон `/` = корень,
`ui::router` отдаёт его и на `/`, и на `/ui`). Разбор argv: `--help` = usage
и код 0, НЕ-флаг аргумент = usage в stderr и код 2 (#191):

```
fasad 0.1.0 cascade-0-only, listening on http://127.0.0.1:8765/health (классов схемы: 8, vault: session/strict, ключ: env)
fasad: UI браузера — http://127.0.0.1:8765/
```

Ключ — 32 байта из любого CSPRNG; `openssl rand -hex 32` в примере только как
самый скучный способ. В `tests/wire_e2e.rs` ключ задан литералом, чтобы CI не
зависел от шелла и от наличия `openssl` на windows-раннере.

### Переменные

| Переменная | Дефолт | Что делает |
| --- | --- | --- |
| `FASAD_BIND` | `127.0.0.1` | Только loopback. `0.0.0.0` = отказ старта, код 2 (проверено процессом: `non_loopback_bind_panics_the_test_instead_of_hanging_it`) |
| `FASAD_PORT` | `8765` | Порт; `0` = свободный, адрес в баннере |
| `FASAD_VAULT_MODE` | `stateless` | `stateless`/`3` — режим SPEC §3.3; `session`/`2` — режим §3.2 |
| `FASAD_VAULT_KEY` | нет | 64 hex-символа (32 байта). Без него ключ эфемерный: метки переживают запрос, но не перезапуск |
| `FASAD_MLOCK` | `strict` | `strict` = отказ старта при отказе `mlock`; `best_effort` = работаем без залоченной памяти. См. §Девиация #55 |
| `FASAD_SCHEMA` | встроенный канон | Путь к `schema.default.json`; содержимое сверяется с вкомпилированным байт-в-байт |
| `FASAD_TAU_LOW` / `FASAD_TAU_HIGH` | `0.20` / `0.80` | Порог экстрактора и верхняя граница уверенности |
| `FASAD_GRAY_LO` / `FASAD_GRAY_HI` | `0.22` / `0.80` | Серая зона τ_arb из #56 п.2; дефолт `τ_low` принят родителем по замеру шага 6 |
| `FASAD_MAX_BODY_BYTES` | `1048576` | Лимит тела. Перелив → 413 в нашем конверте, см. §Fail-closed |
| `FASAD_THREADS` | `8` | Число потоков инференса. На стадии `cascade-0-only` инертен; на смонтированном пути (каскады 1–2) жив: уходит в `LockrExtractor::load`/`DecideArbiter::load` — см. §«Как включить монтаж». Локальные прогоны на машине оператора = 2 (рюлинг 21.10) |
| `FASAD_TIMEOUT_MS` | `3000` | Таймаут наружу: коннект, отправка запроса и TTFB upstream. С шага 7c задействован; отказ — `504 upstream_timeout`. **Сноска (ревью #97): на смонтированном пути это бюджет одного запроса конвейера, и голое число вводит в заблуждение — дефолта там не хватает ни на один Decide-чанк, и даже 8 КБ без серой зоны в дефолт не влезает (2 958 мс на свободной машине против 3 636 мс под фоновой нагрузкой — промер ревьюёра, та же фикстура; для 8 КБ держите ≥ 5 000); нужно `≳ N_lockR·300 + N_decide·8000` мс, промеры — §«Как включить монтаж каскадов 1–2»** |
| `FASAD_READ_TIMEOUT_MS` | `30000` | Пауза между кадрами **входящего** тела (→ `408 read_timeout`) и бюджет чтения **ответа** upstream (→ `504 upstream_timeout`). Две стадии — два кода, см. §Fail-closed п.4 |
| `FASAD_UPSTREAM_ALLOWLIST` | пусто | Список `host[:port]` через запятую, на которые разрешён прокси. Пусто = прокси выключен (`403 allowlist_empty`) |
| `FASAD_PROXY_LOOPBACK_HTTP` | `0` | Разрешить `http://` на loopback-адрес upstream. Нужен тестам и локальным шлюзам; в бою держать `0` |

## Как включить монтаж каскадов 1–2 (шаг 9B, issue #14A)

По умолчанию (`cargo build` без фич) демон собирается и работает каскадом 0:
модельного пути в таком бинаре нет, стадия `cascade-0-only`. Релизный контур
с #181 = полный: `just release-build` собирает с фичей, бандл несёт библиотеку
исполнения (docs/release.md §«Что в бандле»). Чтобы каскады 1–2 были
примонтированы, нужны три вещи разом — фича сборки, веса и библиотека
исполнения.

1. Сборка с фичей (она выключена по умолчанию, и в CI не собирается):

   ```sh
   ORT_PREFER_DYNAMIC_LINK=1 ORT_LIB_PATH=/path/to/onnxruntime/lib \
     cargo build --release --features guard-daemon/ort-inference
   ```

   Env-префикс — не украшение, а условие работоспособности команды на чистой
   macOS: без него release-линковка краснеет на `___isPlatformVersionAtLeast`
   (статика pyke тянет CoreML-хелпер, `docs/model-audit-weights.md` §W2 п.2) — промер
   ревью #97 (2-й раунд) на head этой ветки. Та же строка гейта в теле PR и в
   `docs/release.md` пишется с префиксом: голой её читать нельзя ни в одном из
   двух мест.

2. Веса по раскладке `scripts/fetch-models.sh` (манифест `models/manifest.md`,
   ~880 МиБ, в git не тащим):

   ```
   $FASAD_MODEL_DIR/lockR/rubert-base-pii-ner-onnx/{model.optimized.fp16.onnx,tokenizer.json}
   $FASAD_MODEL_DIR/onnx-community/GLiNER2.5-Decide-ONNX/onnx/{model_q4f16.onnx,model_q4f16.onnx_data}
   $FASAD_MODEL_DIR/onnx-community/GLiNER2.5-Decide-ONNX/tokenizer.json
   ```

   Путь в кеше = `<repo>/<путь-файла-в-репозитории>` (контракт
   `scripts/fetch-models.sh`, шапка «кеш»), у Decide токенизатор лежит в корне
   репозитория, а модели — в `onnx/`; раскладку читает код
   (`cascades.rs:745-749`), промер кэша подтверждает.
   

3. `FASAD_MODEL_DIR` указывает на этот каталог. Не задан — full-бинарь
   (с фичей) **не стартует**: `fasad: старт невозможен: FASAD_MODEL_DIR не
   задан: полный контур требует весов (models/README.md в бандле); каскад-0-only
   — не продакшн-режим` + строка пути докачки (#199) (`ModelsNotConfigured`,
   #185: каскад-0 = харнес/тесты).
   Задан, а модель не загрузилась —
   демон **не стартует**: `fasad: старт невозможен: модельный каскад не загружен:
   нет файла …` (#199: текст += путь докачки UI-кнопкой/скриптом), код выхода 2,
   сокет не биндится. Молча откатиться на каскад 0
   при названных весах = fail-open, его не будет.
   ИСКЛЮЧЕНИЕ КОНТУРА (#198): `fasad-tray` (трей desktop-доставки, win/mac)
   при том же отказе НЕ выходит rc=2, а поднимает ожидающий UI: stage
   `models-pending`, карточка весов с кнопкой «Скачать веса», модельные
   маршруты (`/v1/analyze`, `/v1/anonymize`, `/v1/deanonymize`, прокси) =
   503 `models_pending`; каскад-0-обмана нет (решётка `cascades::startup_pending*`,
   unit-контур). Headless (`fasad`, systemd/докер) = rc=2 как выше.

Переменные, которые с 9B задействованы модельным путём: `FASAD_THREADS` (потоки
инференса lockR и Decide, рюлинг 21.10 для локальных прогонов = 2),
`FASAD_TIMEOUT_MS` (бюджет одного запроса конвейера; выход = `502
cascade_unavailable`), `FASAD_ARBITER_ALPHA` (вес `α` арбитража серой зоны,
по умолчанию 0.5 — не откалиброван, `[claim]`, calibration = issue #85).

Проверка, что монтаж действительно есть (по заголовкам, а не по «вроде
отвечает»):

```sh
curl -s -D - -o /dev/null -X POST -H 'content-type: application/json' \
  -d '{"text":"Иванов Пётр Сергеевич, ИНН 2482014338"}' \
  http://127.0.0.1:8080/v1/analyze | tr -d '\r' | grep -i '^x-guard-'
# x-guard-stage: cascade-0+models   ← модели примонтированы
# x-guard-cascade2: ok              ← лег каскада 2 отработал на этом запросе
```

`X-Guard-Cascade2` = `skipped` означает, что Decide пропущен на входе, который
ломает контракт склейки (в словаре модели `№` = `[UNK]`, issue #88): серые спаны
остаются на вероятности каскада 1 и не теряются, вердиктов каскада 2 по этому
запросу нет.

Что монтаж не делает: не даёт координат каскаду 2 (вердикт уровня строки,
issue #41) и не измеряет себя: бюджет RAM <2 ГиБ проверяется
`scripts/measure-daemon-rss.sh`, цифры — §10 `docs/model-audit.md`, §I1 `docs/model-audit-inference.md`.

Окно экстрактора (256 токенов) с #84 НЕ ограничивает длину запроса: путь
запроса чанкует текст (окно 256 + overlap 32, границы абзац → предложение →
край), прогоны последовательны, спаны возвращаются в байтах оригинала,
пересечения overlap-зоны схлопнуты тем же `merge_disjoint`, что и всё
слияние; чексуммы каскада 0 чанкинг не трогает. Текст короче окна — один
прогон, побитово прежнее поведение (витрина README §4.4 = cmp-гейт). Край
остался, и он честный: если САМ ЧАНК не влезает в окно (байт/4 — верхняя
оценка, а не счётчик: латинская плотность, цифры), ответ — `502
cascade_unavailable` с «чанк не влез даже после чанкинга», а не partial-ответ
без хвоста (Fail-Closed). Латентность линейна по чанкам и дорога на Decide. Пересъёмка 22.10 на базе
`ec9a36b` (post-chunkerfix #111: адванс чанкера якорится от КРАЯ ОКНА, а не от
фактического конца после прилипания к границе предложения), threads=2, тёплый
демон, полный расклад — `docs/model-audit-inference.md` §I1:

- 33 КБ = 38 lockR-чанков = 14.2 с (повтор 13.9 с); было 123 с на 114 чанках;
- 14 КБ = 17 чанков = 5.8 с; было 86.7 с на 90 чанках;
- 8 КБ = 9 чанков = 3.0 с (2 958 мс на свободной машине; та же фикстура под
  фоновой нагрузкой ревьюёра #97 — 3 636 мс, то есть за рамкой дефолта 3000);
- 230 Б = 1 чанк = 289 мс (до #111 тот же вход давал 51 прогон);
- 44 Б = 292 мс (до #111 — 16 прогонов);
- витрина §2 = 285-427 мс, тело ответа бит-в-бит совпало с прогоном 21.10.

На этих входах Decide НЕ звался: ни одного спана в серой зоне (минимальный
score 0.8022 ≥ gray_hi 0.80), short-circuit SPEC §2. Значит таблица — цена
чистых lockR-прогонов, 329-373 мс на чанк (промер 22.10 на свободной машине;
под фоновой нагрузкой ревьюёра #97 та же геометрия даёт 377-445 мс, +15-20 %).
Коэффициент Decide из формулы
(4.5-8.6 с на чанк, промер 21.10) геометрия адванса не отменяет: это цена
одного прогона Decide-окна.

Бюджет поднимают ДО первого смонтированного запроса, а не по факту `502`:
`FASAD_TIMEOUT_MS ≳ N_lockR·300 + N_decide·8000` (мс, threads=2; она же в
доке модуля `cascades.rs`, п.6). Что покрывает дефолт 3000 мс на
смонтированном пути (уточнено ревью #97 — прежняя строка «обслуживает ~1
чанк» была ложью в опасную сторону): каскад-0-only и короткий вход в один
чанок БЕЗ серой зоны — витрина (285-427 мс), 44 Б (292 мс), 230 Б (289 мс).
**8 КБ из этого списка снята (ревью #97, 2-й раунд): это два промера и два
источника — 2 958 мс на свободной машине (промер 22.10, threads=2) против
3 636 мс на машине с фоновой нагрузкой (промер ревьюёра, та же фикстура).
Дефолт 3000 мс 8 КБ НЕ покрывает: «впритык» держалось только на свободном
фоне. Для 8 КБ держите `FASAD_TIMEOUT_MS ≥ 5 000`.** На входе, дошедшем до Decide,
дефолт не покрывает НИ ОДНОГО чанка: первый же серый спан уходит в `502
cascade_unavailable` (выход по бюджету — `Timeout` → 502, `cascades.rs` п.6,
`pipeline.rs`). Практика: формулу считают на своей длине и проверяют
промером. Промеренные точки post-chunkerfix — 14 КБ = 5.8 с и 33 КБ = 14.2 с
без серой зоны; по формуле те же 33 КБ С серой зоной = 38·300 + 24·8000 =
203 400 мс, то есть формула даёт ×14 запаса над промером без Decide — и этот
запас берут, потому что серая зона зависит от текста, а не от длины. Прежняя
точка «8 КБ с серой зоной = 86.7 с ⇒ бюджет ≥ 90 000» снята: число снято с
дефектной геометрии, а его артефакт — документ 14 462 Б, не 8 КБ (`docs/model-audit-inference.md` §I1 п.6).
Чужой масштаб не переносим: своя фикстура — свой промер.

### `POST /v1/analyze`

```jsonc
// запрос
{ "text": "…", "entities": ["inn","snils"], "score_threshold": 0.3 }
// ответ (массив!)
[{ "entity_type": "inn", "start": 27, "end": 37, "score": 1.0, "class": "inn",
   "byte_start": 49, "byte_end": 59, "role": null, "source": "checksum_rf",
   "verdict": "mask_surrogate", "validator": "inn10" }]
```

1. `entities` — фильтр классов; `score_threshold` применяется как
   `max(client, FASAD_TAU_LOW)`: поднять планку клиенту можно, опустить её ниже
   политики сервера — нет.
2. `role` всегда `null` (SPEC §14 — шаг 8).
3. `verdict` ∈ `mask_surrogate | block | audit_only`; политика из
   `X-Guard-Policy`, дефолт `mask`.
4. `source` — кто нашёл, полный перечень (имена фиксирует serde и проверяет
   тест `detection_source_serde_names_are_stable`): `checksum_rf` — чексумма
   российского документа, `checksum_eu` — IBAN, `base64_decode` — та же
   чексумма, подтверждённая **внутри** декодированной base64-нагрузки токена
   (каскад 0, PR #94); `secret_entropy`, `aho_corasick_rule`,
   `gliner_extractor`, `gliner_decide_arbitrator` — каскады 1–2, на стадии
   `cascade-0-only` не выдаются. У первых трёх вес абсолютный
   (`DeterministicW` = 1.0, SPEC §2): источник `base64_decode` отличается
   способом доставки ПДн, а не силой доказательства — окно подтвердил тот же
   валидатор, поэтому вето общее (сверяет
   `crates/guard-types/tests/invariant_checksum_w.rs`).
5. Спан base64-находки указывает на **исходный токен** в теле запроса
   (`byte_start`/`byte_end` — его байты): декодированные координаты наружу не
   отдаются, маскируется ровно то, что прислал клиент. Обход — один уровень
   вложенности, кандидат обязан стоять на пробельной границе; промер
   `поле MjQ4MjAxNDMzOCDQstGL0LTQsNC9 конец` → `byte_start: 9, byte_end: 37`,
   `source: base64_decode`. Правила и контроль ложных срабатываний —
   §«Что каскад 0 находит и не находит» в `docs/daemon-scope.md`.

### `POST /v1/anonymize` / `POST /v1/deanonymize`

```jsonc
// запрос anonymize (режим 2, X-Session-ID: probe), spans — из /v1/analyze + имя руками
{ "text": "Ушакова Кира Саввична, ИНН 2482014338",
  "spans": [{ "entity_type": "person_name", "byte_start": 0, "byte_end": 40 },
            { "entity_type": "inn", "byte_start": 49, "byte_end": 59 }] }
// ответ (промер этой сессии)
{ "text": "Гудзовская Гельфия Хассановна, ИНН [INN_1_G4ETEIV4]",
  "items": [{ "entity_type": "person_name", "start": 0, "end": 21,
              "byte_start": 0, "byte_end": 40,
              "replacement": "Гудзовская Гельфия Хассановна", "operator": "replace" },
            { "entity_type": "inn", "start": 27, "end": 37,
              "byte_start": 49, "byte_end": 59,
              "replacement": "[INN_1_G4ETEIV4]", "operator": "mask" }] }
// deanonymize тем же текстом → { "text": "Ушакова Кира Саввична, ИНН 2482014338",
//                                "substituted": 4, "restore_refused": 0 }
// `restore_refused` — сколько суррогатных форм НЕ развернулось из-за расхождения
// записи со свидетельством выдачи (#60 п.3); на чистой работе 0, ненулевой значит,
// что в тексте остались суррогаты и их видно глазами.
```

1. **Оффсеты: байты — канон, символы — компатибилити.** `byte_start`/`byte_end`
   — авторитетные координаты (наш внутренний контракт, `guard-types::span`);
   `start`/`end` — те же границы исходного текста в **символах**, как у Presidio
   (первичка: `docs/dep-verify-repos.md` п.1–2 п.4 — «offsets символьные»).
   Символьные поля — входные координаты ответа, а не координаты в переписанном
   тексте: после подмены сдвиги правятся, и клиент, читающий `items[].start` как
   позицию в `text`, получил бы неверную якорь-точку. Различающий тест —
   `offsets_are_input_coordinates_not_output_ones`: при двух спанах второй
   обязан остаться на `start = 35`, тогда как координата в переписанном тексте
   уехала бы на ~100 символов вперёд (длина маркера).
2. `spans[].byte_start`/`byte_end` обязаны быть границами символов и не
   пересекаться; ошибка — `422 bad_span` / `spans пересекаются`, до первой
   подмены (полуподменённый текст наружу не уходит никогда).
3. `operator` ∈ `mask` (маркер/метка) | `replace` (суррогат ФИО).
4. `substituted` — число **замен токенов**, а не спанов: одно ФИО в режиме 2
   хранится тремя формами (фамилия/имя/отчество), поэтому промер выше даёт 4 при
   двух спанах. В режиме 3 `substituted` = числу маркеров.
4. Классы, которых нет в схеме, — `422 unknown_entity`.

## Песочница `/ui`

Открыть в браузере `http://127.0.0.1:8765/ui` (порт — из баннера запуска; `DEFAULT_PORT`, `src/config.rs:24`).
Страница зашита в бинарник (`rust-embed`), отдельного фронтенда не ставим:
адрес наружу песочница не берёт ни один, `Content-Security-Policy` на ответах
статики — `default-src 'none'` плюс `'self'` по script/style/img/connect, и в
самой статике абсолютных адресов нет (гейт — факт 4 в `tests/net_audit.rs`).

Что в ней есть: раскраска спанов по уверенности (фон = `score`, рамка = вердикт
`keep_public`/`mask_*`/`block_request`), тултип с классом, скором, валидатором и
байтовыми координатами; фильтр классов (`entities`) и ползунок порога
(`score_threshold` — планку может только поднимать); roundtrip
`anonymize → deanonymize` в session-режиме с кнопкой сброса сессии; чтение
служебных заголовков `X-Guard-*`.

Чего нет, по скоупу шага: настроек демона, апгрейдов, трассировки. Редактор
классов — фильтр запроса, а не смена схемы демона: `PUT /v1/schema` из §8 не
реализован. `schema.json` в ассетах — те же байты, что вшиты в демон, поэтому
оверрайд `FASAD_SCHEMA` песочница не видит (список тогда шире, чем у демона, и
лишний класс просто не приходит в ответе). На `cascade-0-only` ФИО и e-mail не
красятся — это деградация каскада, а не дефект фронта (§«Деградация каскада» в
`docs/daemon-scope.md`).

Отладочная сборка вшивает статику так же, как релизная (`debug-embed`), поэтому
правка `ui/**` пересобирает демон и горячей перезагрузки фронта нет — зато
«статика в бинарнике» проверяется тестом по байтам артефакта.

Объём статики — 20 340 байт на три файла (померено `wc -c`); в §1 п.4 SPEC
заявлен Svelte/Preact ~50 КБ, мы сделали vanilla: сборка продукта не должна
зависеть от node-тулчейна и npm-дерева. Подробно — §«Песочница `/ui`» в
`docs/daemon-scope.md`.

## Хранилище: режимы 2 и 3

| | режим 3 `stateless` (дефолт) | режим 2 `session` |
| --- | --- | --- |
| Маркер | `[[F0#base64url]]`, AES-256-GCM, AAD = id сессии | метка `[КЛАСС_seq_nonce]` + суррогат |
| `X-Session-ID` | не нужен | обязателен (нет заголовка → `400 bad_request`) |
| Хранение на покое | ноль байт | оригиналы в moka-кэше: idle 15 мин, live 2 ч (`Limits::SPEC_DEFAULT`, `guard-vault/src/cache.rs:167-168`) |
| Обратимость | тем же процессом | тем же процессом + тем же `FASAD_VAULT_KEY` |
| `substituted` | да | да |
| Потолок длины оригинала | `MAX_ORIGINAL_BYTES` = **1024 Б** (был 128 Б до #120) | тот же потолок на контейнер; в кэш оригинал проходит до `Limits::max_value_bytes` = 4096 Б |
| Худший размер подмены | маркер 1594 Б (`[[F0#` + 1587 тела + `]]`) | метка ≤ 34 Б, не зависит от спана |

**Потолок длины оригинала — 1024 Б (#120, решение оператора: 128 → 1024).**
Спан длиннее потолка не маскируется: `503 span_too_long` с `len`/`max` в детали
(число `max` печатает константу, а не литерал). Повод поднятия: слой
числительных #118 даёт словесные реестровые номера 170–336 Б (промер по
фикстурам и по словарю `numwords`), и с потолком 128 Б прокси навсегда
отказывал ровно на них; теперь они маскируются, и обратный ход цел (промер:
ИНН-12 словами 223 Б → `200` → `deanonymize` побайтово, `vault_span_cap.rs`).
Вариантов было три (чанковый sealing / необратимая метка / поднятие), взят
третий — обратимость не сужается. ENV-ручки нет намеренно: потолок входит в
размер слота залоченного пула (`POOL_SLOT_BYTES` 512 → 2176 Б; `POOL_SLOTS`
пришлось урезать 64 → 16, чтобы пул 34 КиБ влезал в типичный `RLIMIT_MEMLOCK`
= 64 КиБ: 64 × 2176 = 136 КиБ под такой квотой даёт `Err(Mlock)` = отказ
каждого запроса, промеры 22.10 в доке `POOL_SLOTS`; было 32 КиБ) и в бюджет look-ahead `[[F0#…]]` (1594 Б, был
279 Б) — «подкрутить на ходу» нечего. Session-режим к цене не причастен: маркер
у него 34 Б, оригинал лежит в кэше, лимит кэша (4096 Б на запись, 4 МиБ на
процесс, `Limits::SPEC_DEFAULT`) поднимать не потребовалось — он и был больше
потолка.

1. Нонс в метке (`[INN_1_IZSLOK2S]`, а не `[INN_1]`) — потому что id сессии
   придумывает клиент и он не аутентифицирован: предсказуемая метка означала бы
   подбор чужой сессии перебором. Алфавит метки — `Grammar::LABEL` (`A-Z0-9_`),
   длина ≤ 32.
2. Лимиты реестра: `MAX_SESSIONS = 256` (вытеснение FIFO через
   `engine.invalidate_session`) и `MAX_FORMS_PER_SESSION = 1024` (константа
   `config.rs`, не переменная окружения: шаг 8 меняет её правкой, а не флагом).
   Память демона не должна расти от объёма клиента, и переполнение лимита форм —
   это `422 too_many_forms`, а не тихая потеря формы: потерянная форма дала бы
   partial-restore на `/v1/deanonymize` без ошибки, то есть fail-open на данных.
   Про атомарность: атомарны **ответ и реестр форм**; счётчик меток на
   провалившемся запросе может уйти вперёд (промер 20.10: `[INN_1_…]` → `422` →
   `[INN_3_…]`). Номер метки не секрет, плотность нумерации не обещана, а
   откатывать счётчик означало бы трогать чужой слот
   (`refused_request_moves_only_the_label_counter`).
   Достижимость: на пуле шага 6 (24 леммы) потолок был недостижим вживую и
   проверялся только юнит-тестом с прямой seed-формой
   (`forms_cap_refuses_request_before_first_substitution`); с 768 лемм
   (`pool::SURROGATES_TSV`, шаг 7а) в 6 корзинах и 6 падежах он становится
   достижимым документом примерно на 340 ФИО в одной сессии, то есть из
   страховки превратился в рабочий отказ по данным запроса.
   Дубликаты внутри запроса не резервируются: 400 вхождений одного имени = 3
   формы (`duplicate_forms_within_request_do_not_reserve_twice`).
3. Суррогаты ФИО: столбец `genders` в морф-таблице у именных правил = `f,m`
   (промер 0/56), поэтому `VaultEngine::surrogat_for` на реальных ФИО из
   датасета возвращает `None` — это не дефект хранилища, а его конструкция
   (док `guard-vault::morph` отсылает шаг 6 проверять род по маске). Демон берёт
   род из окончания токена (`suffix_gender`) и вызывает
   `surrogat_for_gender`; при любом сомнении — откат на метку. Ложный род в
   документе дороже отказа маскировать: «Ушакова» → «Тенина», но никогда не
   → «Тенин».
4. `DELETE /v1/sessions/{id}` снимает и кэш оригиналов, и реестр форм; счётчик
   снятого — и в теле, и в `X-Guard-Redacted-Count`. Без `store().sync()` moka
   `iter()` не видит свежие вставки, и teardown вернул бы 0 при живой сессии.
5. Переанонимизация замазанного запрещена (P6, оба режима): спан, содержащий
   нашу метку (`[КЛАСС_СЧЁТЧИК_NONCE]`), наш токен (`[[F0#…]]`) или словоформу,
   которую хранилище этой сессии знает как суррогат, — это `422
   reanonymize_surrogate` **до первой подмены**.
   Причина не в гигиене протокола, а в ключе реверс-индекса: он устроен по
   суррогату (`guard-vault::VaultEngine::original_of_surrogat`,
   `StoreKey::new(session, "SRG#" + form)`), поэтому повторная анонимизация собственного выхода
   перезатирает раннюю связь, и `deanonymize` начинает возвращать смесь чужой
   фамилии с настоящими именем и отчеством как настоящие `ПДн` (промер: три
   раунда → `200 OK` + «Ветрова Кира Саввична»). В режиме 3 тот же класс
  был тише: два раунда на одном токене давали `deanonymize` с
   `substituted: 1` и живым `[[F0#…]]` внутри «восстановленного» текста —
   partial-restore без ошибки. Проверка по любому классу, не только по
   `person_name`: дефект в ключе, а не в типе данных. Ложный отказ
   возможен, и не только на ФИО: легитимные `ПДн` могут совпасть по форме с
   нашей подменой (пароль `[AB_12]`, фамилия, совпавшая сгенерированной).
   Предпочтение отдано ложному отказу: тихая подмена данных неотличима от
   правды, а `422` клиент видит и разберётся сам. Из корневой правки (ключ с
   оригиналом, отказ на неоднозначном развороте) шаг 7d сделал второе: ключ
   кэша остался формным, а отказ на неоднозначном развороте держит реверс-индекс
   `(сессия, форма)` → ключёвый отпечаток подставленного оригинала
   (`Vault::unrestored_mismatch()`, см. `docs/daemon-scope.md` §«Профиль риска
   суррогатов»). Остаточный риск этого индекса назван числом: вероятность
   молчаливой подмены в перенятом слоте `p ≈ 2⁻⁶⁴` на одно событие (отпечаток
   выдачи усечён до 8 байт), оценка ожидания на срок жизни демона — порядка
   `5·10⁻¹⁵` подмен. Первое (дедуп падежных форм по лемме,
   а не ключ по словоформе) — отдельная задача #65.

6. Коллизии слотов суррогатов: измерено, типизировано, деградировано в метку
   (B2/P8 → шаг 7а, #60). На пару (род, тип) приходится 128 лемм внешним
   артефактом `data/morph/surrogates.tsv` (генератор `scripts/surrogen.py`,
   первичка — падежные таблицы petrovich, MIT; артефакт закреплён тестом
   `pool::tests::pool_artifact_is_pinned`), выбор — FNV-1a по лемме оригинала
   (`guard-vault::pick_surrogat`). Промер коллизий —
   `guard-vault/examples/pool_probe.rs` на golden-v1, метрика: пары ФИО, где
   **разные** оригиналы лезут в один слот (пара с общим токеном коллизией не
   считается: там один владелец, и движок не отказывает). 27 имён на
   суррогатном пути, 351 пара: пул 4/корзину (состояние шага 6) — 218 пар =
   62.1 %; 16 → 15.4 %; 32 → 7.1 %; 64 → 4.0 %; **128 → 6 пар = 1.7 %** при
   цели #60 «< 5 %». Тот же промер 20.10 в других единицах (пересчёт ревьюера
   #58 по выдаваемым формам): 347 совпадений имён по позициям в 351 паре, 248
   пар с общим слотом, 218 отвергаемых при выдаче — отказная метрика ниже,
   потому что в парах с общим токеном владеет один оригинал и first-writer-wins
   идемпотентен. Историч. промер того же шага: 56 уникальных ФИО в наборе, 27 на
   суррогатном пути, 15 развёрнуты чужим именем; ревьюер независимо промерил 384
   из 400 ФИО в свежей сессии не в своём слоте при `substituted: 9`.
   Что делает демон на коллизии: имя уходит на типизированную метку
   `[PERSON_NAME_n_nonce]`, запрос остаётся `200`, разворот обоих имён —
   byte-exact. Отказом это было ровно один шаг (`422 surrogate_collision`) и
   ломало весь документ из-за косметики, поэтому вариант ошибки удалён из
   `VaultApiError` целиком: метка точна, коллизий не имеет и обратима, ветки
   «метка тоже невозможна» не осталось (слишком длинная метка — это и есть
   `422 too_long`, как у любого класса). Движок при этом по-прежнему
   first-writer-wins: тихой подмены нет ни при каком пуле
   (`surrogate_slot_refuses_second_original_and_keeps_the_first` на синтетической
   корзине из одной леммы, `surrogate_pigeonhole_refuses_within_pool_plus_one`),
   а демон переводит его отказ в метку
   (`second_name_on_taken_slot_falls_back_to_label`,
   `two_colliding_names_in_one_request_send_the_second_to_a_label`,
   `collision_on_second_token_sends_whole_span_to_label`,
   `batch_precheck_disagreement_rolls_the_partial_span_back`,
   `pending_forms_marks_second_owner_of_one_form_taken`,
   `two_names_in_one_session_mask_and_restore` — экс-KNOWN-RED ревьюера #58).
   Деградация видна наружу без всякого отладочного режима: `GET /health` отдаёт
   объект `vault` с `surrogate_fallbacks` (имена, отданные метке вместо гладкой
   подмены; растёт — пул мал для профиля имён) и `unrestored_mismatch` (сколько
   разворотов отвернулось, потому что форма в кэше указывает не на тот оригинал,
   который в неё подставлялся, — шаг 7d, `docs/daemon-scope.md` §«Профиль риска
   суррогатов»).
   Побочный эффект, принятый осознанно: до отказа (любого) в кэше движка могли
   записаться формы с невыданным токеном. Реестр форм демона о них не знает,
   `deanonymize` ходит по реестру — такая запись недостижима и снимается TTL или
   teardown; откатывать её нельзя, потому что откат трогал бы чужой слот.
   С шагом 7d у этого принятого эффекта вырос хвост: индекс помнит осиротевшую
   форму до teardown сессии, то есть после истечения `idle`-лимита она не
   освобождается, а продолжает отказывать второму владельцу. Цена — лишний
   отказ внутри одной сессии, и он не молчит: растит `surrogate_fallbacks`.
   Выигрыш — свидетельство о подмене не тонет вместе с записью кэша.
   Пачка форм одного спана атомарна: при отказе на любом токене `PendingForms`
   откатывается `truncate`-ом до начала спана, и половина имени в суррогат,
   половина в метку не выходит. Ветка живая, а не страховочная: пред-проверка
   батча помнит владельца формы по **поверхности** токена, движок — по **лемме**,
   и один человек, написанный в двух спанах с разным регистром имени («Кира» и
   «кира»), для батча — два владельца одной формы; отказ наступает на втором
   токене, первый уже в пачке. Дискриминировано промером возмущением: с
   закомментированным `truncate` краснеет ровно
   `batch_precheck_disagreement_rolls_the_partial_span_back` (`forms_len` 4
   вместо 3), остальные 83 теста зелёные.

## Девиация #55: `mlock` (задокументирована, а не замолчана)

`#55` (контракт залоченной памяти) **не подписан**. Реализация `guard-vault`
ложит буферы через `mlock(2)`/`VirtualLock`, и мы не утверждаем наружу, что
память не свопится, ни на одной платформе: исход `mlock` при исчерпании лимита
платформозависим, а промера «гарантия на macOS» у нас нет. Что промерено в этой
сессии — так это то, что `strict`-старт на macOS-arm64 проходит (баннер
`vault: stateless/strict`), а отказ залочки у нас не молчание, а явная политика.

Что делает демон:

1. `FASAD_MLOCK=strict` (дефолт) — при отказе `mlock` **старт не состоится**
   (код 2, причина в stderr). Молча залочить «столько, сколько дали» = соврать.
2. `FASAD_MLOCK=best_effort` — работаем без залочки; в баннере это видно
   (`vault: session/best_effort`), т.е. деградация наружу, а не внутри.
3. Целевая платформа контракта — Linux (CI-матрица: ubuntu-24.04 + windows-2022,
   `ci.yml:23`; контракт залочки проверяется на linux-джобе, на windows у него
   своя ветка — п.4); macOS остаётся дев-средой, и именно поэтому девиация
   названа, а не «починена молча на одной машине».
4. Известный риск windows-раннера: `VirtualLock` там падает на квоте
   залочиваемых страниц процесса (`ERROR_NOT_ENOUGH_QUOTA` — помечено `[claim]`
   в доке `guard-vault::token::VaultError::Mlock`, промера с этого хоста нет).
   Ручка `FASAD_MLOCK=best_effort` это снимает, но в тестах и в CI мы её НЕ
   выставляем: красный windows-CI на `strict` = вопрос к контракту #55, а не
   флак, и он должен быть услышан.
5. На `X-Guard-*` отказ хранилища не маскируется: `503` с причиной в конверте
   (`code` + `message`), без имени модуля и без текста входа (там может быть
   кусок ПДн).

| Код | Когда | Тело |
| --- | --- | --- |
| `400` | `X-Guard-Policy` с непечатаемыми байтами; `X-Session-ID` вне печатаемого ASCII (`HeaderValue::to_str` отказывает и на управляющих байтах, и на 0x80-0xFF) — отдельно от «заголовка нет»: клиент, приславший мусор, не должен слышать «у вас нет заголовка»; тело не JSON; тело оборвалось битым фреймом (`bad_body`) | `{"error":{"code","message"}}` |
| `413` | тело больше `FASAD_MAX_BODY_BYTES` | `{"error":{"code":"body_too_large",…}}` — наш конверт, а не текст axum |
| `422` | класс не знает схема; спан не на границе символа; пересечение спанов; маркер не разворачивается; метка длиннее лимита; пустой оригинал; форм суррогатов больше лимита (`too_many_forms`); вход — уже замазанный нашим же механизмом, в любом режиме (`reanonymize_surrogate`) | конверт выше |
| `403` | прокси: allowlist пуст, хост не в списке, `http` без loopback-исключения | конверт |
| `408` | входящее тело молчит дольше `FASAD_READ_TIMEOUT_MS` (между кадрами, не суммарно) | `{"error":{"code":"read_timeout",…}}` |
| `502` | upstream недоступен (`upstream_unreachable`), TLS не установился, пришёл `3xx` (любой, включая `304`: `ureq` при `max_redirects = 0` не ошибается, ловим по статусу), протокол нарушен, ответ оборвался посреди тела (`upstream_aborted`), запрос снят | конверт, `code` называет стадию |
| `504` | upstream не уложился в таймаут (коннект/отправка/TTFB — `FASAD_TIMEOUT_MS`; чтение тела — `FASAD_READ_TIMEOUT_MS`, и на стриме это бюджет **всей операции**, а не пауза между байтами: idle-лимита между чтениями у `ureq` нет, длинную генерацию настраивают поднятием ручки) | `{"error":{"code":"upstream_timeout","message":"…на стадии <name>"}}` |
| `503` | **любой** `VaultError` (на практике `Busy` / `Mlock` / `Entropy`; `TooLong` — спан длиннее `MAX_ORIGINAL_BYTES` = 1024 Б, потолок поднят 128 → 1024 в #120, см. §«Хранилище» ниже) **или** паника обработчика | конверт; для паники `code: internal_panic`, для `TooLong` — `code: span_too_long`, `message: vault:span_too_long len=<n> max=1024` (число `max` автоизводно из константы, не литерал; ревью #118 B2: отказ обязан называть причину) |
| `500` | ошибка скоринга в конвейере | конверт |

1. Ни одного «успешного» ответа с частичным результатом: неразвернувшийся маркер
   = `422`, а не текст с остатком маркеров.
2. Отказ хранилища наружу не называет внутренних модулей: категория — плюс
   числа лимита там, где причина вычислима без ПДн. `TooLong` — ровно такой
   случай: `len`/`max` это метрики, а не текст входа; подставная причина
   («хранилище отказало» там, где спан просто не влез в потолок) отправляла
   клиента чинить не то — правка B2 (#118), тест
   `vault::tests::over_long_span_refusal_names_the_reason_not_the_vault`.
3. Лимит тела считается по **фактически прочитанным байтам**, `Content-Length`
   не доверен; заголовок можно соврать. Ошибка потока при этом отличается от
   перелива: битый chunked даёт `400 bad_body`, а не `413`. Штатно различить
   было нечем — `is_length_limit()` в axum-core 0.5.6 нет (промер исходника
   crate), и через `to_bytes` любое исключение становилось «слишком длинно»;
   врать о причине той же ошибкой = тот же fail-open в диагностике. Тест —
   `broken_chunked_body_is_400_bad_body_not_413`.
4. **Время чтения тела ограничено: риск P5 из ревью PR #58 закрыт на шаге 7c.**
   Промер шага 6: тело из 52 байт, накапанное по байту за 0.6 с (~24 с на
   запрос), давало `200 OK`. Теперь пауза между кадрами входящего тела дольше
   `FASAD_READ_TIMEOUT_MS` стоит клиенту `408 read_timeout`, и это отдельная
   ручка, а не `FASAD_TIMEOUT_MS`: та названа таймаутом наружу, переименовывать
   смысл = врать об имени. Проверено процессом —
   `slow_client_body_is_408_read_timeout`: капает тело по байту тем же способом,
   что был в промере. Тот же бюджет на чтении ответа upstream даёт `504
   upstream_timeout`, а не `408`: ждали в этот раз не клиента.
5. Паника обработчика перехватывается (`http::guarded`) и становится `503`, а не
   разорванным соединением; сообщение паники наружу не цитируется (в него может
   попасть вход), хук в `main.rs` печатает только `файл:строка`.
6. `Zeroizing<String>` на буферах с оригиналами: тексты всех трёх запросов и
   ответ `deanonymize`. `Anonymized.text` — обычный `String` осознанно
   (оригиналов в нём нет по построению). `Debug` на запросах печатает
   `[REDACTED]`.
7. Общий лог-канал отказов — один: на `5xx` пишется `fasad: отказ <статус>
   code=<код> detail=<message>` (`ApiError::into_response`, ревью #118 B2:
   оператор в логе обязан видеть ту же причину, что видит клиент, а не факт
   «отказали»). Новой поверхности раскрытия это не добавляет: `detail` — ровно
   то, что ушло в теле ответа. Текст входа и id сессий в него не попадают: на
   `5xx` сообщение собирается из наших строк, чисел лимитов и подрядных строк
   `ort` (имена стадий/файлов модели). `4xx` в stderr не пишутся. Сверх этого
   на прокси-пути живут два отладочных зонда (`proxy.rs:207,212`, «ПРОБНИК
   unreachable», «ПРОБНИК ureq»): печатают `Debug` вендорной ошибки — имя хоста
   и фаза таймаута, текста входа там нет; атом #118 их не трогал, вынос —
   отдельная гигиена.

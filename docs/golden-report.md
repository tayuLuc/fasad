# Golden-report: union-recall полного каскада на golden-наборе

Гейт **#14, часть B** (SPEC §5 п.6; в `AGENTS.md` и `data/golden/README.md` тот же пункт
именуется «§5 п.7» — сдвиг нумерации между файлами, владелец — SPEC, правка не здесь).
Промер 21.10.2026. Первичка = сырой вывод прогона (§8); документ сгенерирован из него
`tools/metrics/render_report.py`, числа руками не переписываются.

## 1. Планка и формула

- Требование: **recall ≥ 98 %** на эталонных примерах (SPEC §5 п.6), меряется только по
  нашему `data/golden/`; чужие «99 %» из README не цитируются как наши (AGENTS,
  «Дисциплина фактов» п.4).
- Промер CI (`docs/dep-verify-algorithms.md` §8): при N=50 планка **статистически
  непроверяема** — 48/50 = 86.540–98.896 %, а 50/50 даёт нижнюю границу 92.865 %;
  отсюда «golden-набор расширяется до N≥150» `[verified 18.10]`.
- Формула — Wilson interval, z = 1.959963984540054. Харнес на старте сверяет три
  anchor-строки §8 (48/50, 49/50, 50/50) и падает при расхождении > 0.01 %:
  зелёный CI без этого self-теста = ничто (реестр ложно-зелёных).
- **Рюлинг оператора 21.10 (записан в issue #77):** планка = **нижняя граница Wilson
  ≥ 98 %** на **span-уровне**, определение попадания = **byte-exact** (контракт
  `data/golden/README.md`). Значит **гейт-метрика этого документа = `exact /
  union_span`** (число в §5.5); overlap остаётся диагностикой — он язык Rust-харнеса
  (`recall_golden.rs`, `wilson_lower`), расхождение меряется в §6.4. Text SPEC и
  абзац README правит владелец файла (#77); здесь метрика уже считается по рюлингу.

## 2. Знаменатель (N-гейт)

- `data/golden/golden-v1.jsonl`, sha256 `546d8c3593d4e7df…`
  (сверяется с константой гейта B2 `GOLDEN_V1_SHA256`, прогон падает при дрейфе):
  рядов recall **150**, gold-спанов recall **358**;
  отрицательных рядов 54 (bait-спанов 24).
- Support по классам (gold-вхождения): person_name 56, inn 36, snils 29, ogrn 25, ogrnip 21, iban 27, address 40, card_pan 32, phone 36, email 40, passport 16.
- **N-гейт закрыт**: rows 150 ≥ 150 и spans 358 ≥
  150 ⇒ ветка «планка N не покрыта, требуется +M аннотаций» не требуется;
  синтетикой знаменатель не раздували.
- По уровням планка проверяема по-разному (`UNION|ci_probe` — минимум k, при котором
  нижняя граница Wilson уже ≥ 98 %):
  - n = 16: нужно k ≥ 17 > n ⇒ планка **непроверяема ни при каком k**;
  - n = 150: нужно k ≥ 151 > n ⇒ планка **непроверяема ни при каком k**;
  - n = 358: нужно k ≥ 357 ⇒ допуск ровно 1 промах на 358;
  Итог: на уровне **класса** (support 16–56) планка 98 % непроверяема — это и есть
  следствие §8; метрика уровня гейта = union по всем gold-спанам recall-выборки,
  где n ≥ 150 выполняется.

  **CI-дисклоузер по знаменателям** (та же формула §8; при k = n нижняя граница
  равна n/(n+z²), z² = 3.84146 — промер 21.10):

  | знаменатель | n | lo Wilson при k = n | планка 98 % проверяема? |
  |---|---|---|---|
  | recall-строки | 150 | 97.503 % | **нет**: k ≥ 151 недостижимо; min n = 189 |
  | recall-спанов | 358 | 98.938 % | **да**: k ≥ 357, допуск ровно 1 промах |
  | уровень класса | 16–56 | ≤ 93.581 % (при n = 56) | нет ни при каком k |

  Формулировка гейта «N ≥ 150» выполнена и на строках, и на спанах; статистически
  планка проверяема **только по спанам** и с допуском ровно в один промах (k ≥ 357,
  lo(357,358) = 98.4350 %). Это арифметика §8
  (там же N ≈ 140 при p̂ = 98 % и N ≈ 176 при p̂ = 99 % — меньшие n потому, что
  p̂ < 100 %).
- 73 из gold-спанов (iban 27, ogrn 25, ogrnip 21) — классы с чексуммой, вне ONNX-
  инвентаря моделей: в `docs/model-audit.md` §5.7 C они **исключены из знаменателя**
  (285 из 358). Здесь знаменатель = все 358: union-каскад обязан накрывать и их,
  иначе метрика измеряет не каскад, а половину каскада.

## 3. Метод: что такое union

Инструмент `tools/metrics/union_recall.py`. Span засчитан, если его поймал **любой**
каскад (τ — порог вероятностных стадий; чексуммы имеют score 1.0 и порогом не режутся):

1. **Каскад 0** — продуктовым путём: `POST /v1/analyze` с `X-Guard-Policy: audit_only`
   на собранном `target/debug/fasad`; координаты — `byte_start`/`byte_end` из ответа.
   Это не вторая реализация чексумм, а тот же код, что в проде.
2. **Каскад 1** — lockR `model.optimized.fp16.onnx` (runtime-квант), span-level,
   `conf ≥ τ`. Декодер импортируется из `tools/verify/parity_golden.py` — оракул один
   (рецидив «три харнеса = три метрики» закрыт импортом, а не договорённостью).
3. **Каскад 2** — Decide `model_q4f16.onnx` (runtime-квант), row-level P(yes) ≥ τ,
   8 вопросов в рантайм-порядке блока схем (issue #53), `№` → пробел, sanitize_state;
   контракт `crates/guard-onnx/examples/recall_golden.rs`, воспроизведён 1-в-1.

Сопоставление — **byte-overlap** (контракт Rust-харнеса) и вторая мера
**byte-exact** (контракт `data/golden/README.md`); расхождение меряется явно (§6.4).
`strict` = только каскады с координатами (0 и 1), без row-level кредита.

**Дискалоузер завышения (прочитать до того, как брать union в отчёт).** Каскад 2
отвечает на ряд, а не на span: «в этом ряду есть класс X». Харнес засчитывает за это
**каждый** gold-спан класса X в ряду. В рядах с 2+ спанами одного класса кредит шире,
чем у span-каскадов; это контракт `recall_golden.rs` (`decide_counts`), унаследованный
union'ом без изменений. Поэтому агрегатов три: `union_span` (с row-кредитом),
`strict_span` (только координатные каскады), `union_row` (доля рядов с хотя бы одним
пойманным span'ом). В отчётах наружу мера называется полным именем.

Отрицательный split (54 ряда, 24 bait-спанов) меряется отдельно (§5.3): union-метрика
FN-ориентирована (SPEC: FN фатален, FP дёшев), без FP-контроля она бессмысленна.

## 4. Воспроизведение

```sh
cargo build --bin fasad          # каскад 0 = продуктовый бинарь
just union-recall --thr 0.20,0.25 \
    --sweep 0.10,0.15,0.20,0.25,0.30,0.40,0.50 --out /tmp/union_r1.jsonl
uv run --locked python tools/metrics/render_report.py \
    /tmp/union_r1.jsonl docs/golden-report.md
```

Окружение промера: python 3.13.13, onnxruntime 1.31.0,
numpy 2.5.4, Darwin-arm64; **потоков инференса =
2** (intra/inter_op), niceness 10,
seed: n/a-no-RNG (RNG в пайплайне нет).

- Число потоков — часть воспроизводимости: §5.7 зафиксировал, что на Decide
  `--threads 4` против `8` двигает счёт на 1 tp (ORT intra-op флипы в p-полосе),
  lockR инертен. `OMP_NUM_THREADS` на нашей сборке инертен — вендорный
  `libonnxruntime.1.31.0` osx-arm64 собран без OpenMP (первичка ревьюера #73,
  otool/strings); рычаг = intra/inter_op сессии и `FASAD_THREADS` демона.
- Рюлинг оператора 21.10 (AGENTS §3 п.3): `nice -n 10`, 2 треда, один прогон за раз,
  сетка τ — последовательно. **Метрика снята в щадящем режиме**; на величину recall
  потоки не влияют (детерминизм при фиксированных потоках), влияют на время — §8.
- Детерминированность подтверждена повтором прогона (тот же командный ряд, те же
  `--threads 2`), сверка по **целочисленным** строкам, а не по float-формату:
  ```sh
  diff <(grep '^UNION|' /tmp/union_r1.jsonl | grep -v '^UNION|cascade0') \
       <(grep '^UNION|' /tmp/union_r2.jsonl | grep -v '^UNION|cascade0')   # пусто
  ```
  Строка `UNION|cascade0` исключается осознанно: в ней порт и tmp-путь демона
  (заведомо недетерминированные поля, не метрика).
- `TIME|`-строки второго прогона **не** сравнимы с первым: r2 шёл параллельно
  с `cargo clippy --workspace --all-targets` (нарушение «один прогон за раз»
  рюлинга 21.10, фиксируем как дефект процедуры), поэтому время в них завышено
  конкуренцией за ядра. На `UNION|`-счёта это не влияет (детерминизм при
  фиксированных потоках), на длительность — влияет.
- Входы (sha256 из `PRECHECK|`/`UNION|sha|`, сверяются на старте прогона, прогон падает
  при расхождении с `models/manifest.tsv` и SPEC-пинами):
  - `golden-v1.jsonl` — `546d8c3593d4e7df6b9fb51912d8a18440192293168940b60ff0ed99b7d187ae`
  - `model.optimized.fp16.onnx` — `039aba6be0c64f50f37c64ddc6c6d4e2fd91cbdcf5c9291056ec6bc96c70a501`
  - `model_q4f16.onnx` — `93f3e0d4ed8bbd4858840f8a2e66028a70e86a482e1ff9822d2ac726381684f6`
  - `model_q4f16.onnx_data` — `df2b05dc97ff875e0d2b51ec21de0049b7b3e7feddaa5224d318dc79e66210e8`
  - `schema.default.json` — `039133c07bcca89b86eb8bdd40b39b3deae8fffcc1ddbcc83070bad5c7c65a24`
  - `tokenizer.json` — `3ad87d9ffe669147063e70850927dd2da90249e2acc5c8527f1eb65df467bcc8`

## 6. Находки промера

1. **Дыра продуктового покрытия каскада 0.** Демон отдаёт только чексуммно
   валидируемые классы; `person_name`, `phone`, `email`, `address`, `passport` в
   продукте не детектируются вовсе — модели в демон не смонтированы
   (`X-Guard-Stage: cascade-0-only`, `pipeline.rs` L17-19). Значит «union каскада
   целиком» в этом промере = **композиция харнеса** (демон + две ONNX-сессии),
   а не путь продукта. Гейт #14 закрывается только монтажом каскадов 1/2 в рантайм.
2. **Корень почти всего дефицита — нормализация формата номера (issue #51), а не
   качество моделей.** Промер промахов каскада 0 по составу значения (разведочный
   скрипт на том же демоне через `/v1/analyze`, координаты байтовые):
   - `snils`: 28 промахов из 29, **все 28 форматированные** (`378-312-074 87`),
     обычных промахов — 0 (`c0` = 1/29, и этот один именно обычный вид);
   - `card_pan`: 15 промахов, **все форматированные** (`2204-9947-4132-9761`);
   - `iban`: 21 промах = 18 форматированных (`RU19 0445… ` через пробел) + 3
     обычных валидных (24-символьные ES-семейства, `ES6987181615681144316009`).
   Чексуммный валидатор требует compact-вид; детектор не нормализует разделители
   перед проверкой ⇒ вето не срабатывает, score 1.0 не выставляется, span теряется
   на каскаде, который по определению не промахивается.
3. **Состав IBAN-набора** (промер по датасету): 27 span'ов, длины compact 16–33,
   префиксы BE, DE, ES, FR, NL, RU; mod-97 — валидны все 27 (разведочная
   перепроверка, не оракул ожидаемого значения). Каскад 0 накрывает 6, хвост
   закрывается не моделью: нормализация (#51) + покрытие длин/стран в валидаторе
   (таблица счетов первичкой не закрыта: SPEC §11 п.6, AGENTS §Дисциплина п.3).
4. **Расхождение оракулов и направление смещения координат** — метрика чувствительна
   к определению попадания; направление смещения померено отдельно, не угадано:
   при τ = 0.20 тот же прогон даёт union 92.46 % по overlap и
   91.34 % по byte-exact (k 327/358 против
   331/358); по строгой координатной мере разрыв
   89.11 % (overlap) против
   40.22 % (exact).
   Промер `tools/metrics/probe_coords.py` (τ = 0.20, lockR fp16, 2 треда, артефакт
   в §8.1): из 503
   перекрывающихся пар предсказание/gold — 465
   лежат **целиком внутри** gold-границ, 38 точных,
   superset = 0, partial = 0.
   Направление: **модель недо-сегментирует (режет хвосты)**, а не «шире» gold:
   d_start медиана 5 (min 0 — начало
   никогда левее gold, max 42), d_end медиана -8
   (max 0 — конец никогда правее gold; в 80.1 %

   усечённый спан лежит

   в генераторе, а не в тексте (иначе следующая генерация вернула бы ошибку).

   «exact», Rust-харнес — «overlap». Это дефект определения метрики, не модели —
   заведён в **#77**; рюлинг 21.10 выбрал byte-exact (см. §1, §5.5).
5. **Row-level кредит Decide** (§3) завышает `union_span` над `strict_span`:
   при τ = 0.20 это 92.46 % против 89.11 %
   (k 319 против 331 при n = 358).
6. **Потоки**: записаны в метод (§4), иначе повтор прогона не обязан сойтись с числами.
7. **`data/golden/README.md` §«Метрика recall» содержит устаревшее CI-число**: «нижняя
   граница ≥ 94.5 % при 146/146». Промер формулой §8: при n = 146 и k = n граница
   = 97.436 %; 94.5 % соответствует n ≈ 67 (94.577 %). Число пережито ростом набора
   (v1.0 → v1.1) и не пересчитано — правка в README, не здесь.
8. **У планки три владельца с разными формулировками**: SPEC §5 п.6 («recall ≥ 98 %»,
   без уточнения точка/граница), README («≥ 98 % при N=146+, нижняя граница ≥ 94.5 %»),

   жёсткий вариант). Пока владельцем не выбран один, «гейт закрыт» — слово с тремя
   значениями. Прогон печатает и точку, и границу, не выбирая за SPEC. **#77**.
9. **Отрицательный сплит недо-размечен, «FP» по нему неизмерим.** Каскад 0 на

   все 5 — валидные ПДн: `2200000000000004`, `5555555555554444`, `378282246310005`,

   score 1.0. То есть детектор прав, а метки не покрывают реальную ПДн в строке.
   По определению README («FP = пойманный спан на месте **не-PII**») это не FP.
   Следствие: FP-контроль читается только по bait-счётчикам (каскад 0: 0/24 —
   декорации отброшены чексуммами; lockR: 9/24 — model-bait проходит). Правка
   датасета: размечать реальные номера в negative-строках, иначе FP-гейт
   ложно-красный на правильном поведении. Заведено как **#78**.
10. **Самопроверка координатной шкалы** (класс инцидента «координатное смещение»).
   Первичная сверка: gold-координаты = байтовые (g0001 `person_name` [87,127),

   указывают на прозу» — 98/117 ложных хитов) записан, чтобы урок не потерялся:
   прежде чем заявлять про чужие координаты, надо проверить, своей ли рукой они
   нарезаны.

0. Детерминированность подтверждена повтором: `diff` по `UNION|`-строкам двух прогонов

   exact), а не полагаться на row-level кредит. Направление правки задаёт промер §6.4:

   по классам: `iban` 21 + `snils` 6 (сверка: 358 − 331 = 27 ✓). План:

   при этом остаются дефектом качества моделей — на текущую планку они не влияют,

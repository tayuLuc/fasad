# fasad — локальный AI-гард: спецификация для сборщика-агента

> Статус: **гипотеза, вторичный источник**. Вся фактура ниже — из транскрипта
> диалога с LLM-ассистентом (носитель удалён; детали в `docs/source-note.md`) и не проверена по первичке.
> Каждый пункт помечен: `[claim]` = утверждение модели, требует кросс-чека перед
> тем как становиться кодом; `[decided]` = принятое командой направление.
> Правила fidelity: `process-rules-knowledge-wiki` (fact from secondary = claim),
> `process-rules-knowledge-wiki` § snapshot-is-prior-art (снапшот версий протухает).

## 0. Что это (одна строка)

Одиночный нативный демон-стендэлон (Linux + Windows), локальный «AI-брандмауэр»:
размечает входящий текст по категориям конфиденциальности, принимает решение
MASK/KEEP, обратимо подменяет секретные спаны, проксирует запросы к внешней LLM.
Полностью оффлайн, без Python/Docker-рантаймов, бюджет <2 ГБ, латентность 80–300 мс.

## 2. Пайплайн (4 каскада)

### Каскад 0 — детерминированный (<1 мс) `[verified 18.10, docs/dep-verify-algorithms.md]`
- Regex O(n) (`rust-lang/regex`) + контрольные суммы (эталонные векторы — таблицами
  в `dep-verify-algorithms.md`, не пересчитывать их той же функцией, что проверяется):
  - ИНН 10/12: mod 11; веса порождаются удвоением по mod 11 (список «57 36 21 17» —
    **галлюцинация, опровергнута**); приказ ММВ-7-6/534@ (утратил силу с 2017;
    действующую редакцию искать через ФНС).
  - СНИЛС: веса 9..1, mod 101, 100/101 → «00»; первичка добавила: проверка только
    для >001001998, запрет трёх одинаковых цифр подряд.
  - ОГРН-13: mod 11; **ОГРНИП-15: mod 13** (замер 3/3; «mod11 ×4 %10» из спеки —
    опровергнут; «×4 %10» = артефакт пересказа, писать «младшая цифра остатка»).
  - Карты: Луна по ISO/IEC **7812-1:2017**; «Мир» = **весь префикс 22xxxx** (заявка
    2200–2204 опровергнута правилами НСПК v4.4: 78 % наблюдаемых BIN мимо).
  - БИК: чексуммы нет (383-П подтверждён); ^04 + спец 000/001/002 + перекрёст
    БИК[1:3]==счёт[6:8]; план счетов **809-П** (не «385-П/2020»; 579-П отменён с
    01.01.2023, п.3 809-П; детали — `docs/dep-verify-algorithms.md` §7a).
  - **IBAN в РФ существует** (SWIFT REGISTRY rel.99 §2.71, effective Apr-23, 33,
    mod-97; последняя позиция BBAN `!c` — не жёсткий \d); «в РФ IBAN нет» из
    транскрипта **опровергнуто**.
  - Base64-обход (не транскрипт, добавлено PR #94): токен алфавита
    base64 на пробельной границе декодируется **одним** уровнем, и окно внутри
    нагрузки подтверждает тот же валидатор схемы. Вес такой находки —
    `DeterministicW` = 1.0 наравне с `checksum_rf`/`checksum_eu` (источник
    `base64_decode`): способ доставки ПДн не меняет силу доказательства.
    Вектор весов — контракт, его сверяет
    `crates/guard-types/tests/invariant_checksum_w.rs`; правка вектора =
    правка этого пункта, не рефакторинг. Координаты — исходный токен,
    декодированные байты наружу не отдаются. Инвентарь:
    `docs/cascade0-inventory.md` §1.3, §2.2.
  - Числительные словами (не транскрипт, добавлено issue #51 п.2): количество,
    записанное словами, собирается в цифры слоем
    `crates/guard-daemon/src/numwords.rs` и прогоняется по **тем же** окнам и
    валидаторам схемы; координаты — исходная фраза словами (тот же контур
    кредитации, что у base64-атома). Вес находки — `DeterministicW` = 1.0,
    источник остаётся `checksum_rf`/`checksum_eu`: доказательство то же
    (чексумма), а происхождение спана видно по самому спану, поэтому восьмой
    вариант `DetectionSource` не заведён и вектор весов не правится. Порог
    слоя = 9 цифр (самая короткая сущность таблицы длин), поэтому года словами
    спана не дают. Покрытие и цены — §4 и
    `docs/daemon-scope.md` § «Что каскад 0 находит и не находит». Инвентарь:
    `docs/cascade0-inventory.md` §1.4, §2.1.
- Секреты по образцу сканеров: двухфазный префикс-префильтр (`AKIA`, `ghp_`, `sk-`,
  `eyJ`, `xoxb-`) через `aho-corasick` → тяжёлая regex в окне ±200 байт → энтропия
  Шеннона + Probability-of-Randomness. Референсы architectures: `mongodb/kingfisher`
  (Tree-sitter контекст: токен должен лежать в строковом литерале/присваивании,
  не быть именем функции или тестовой заглушкой), `praetorian-inc/noseyparker`,
  `sirwart/ripsecrets`. Live-верификацию токенов как у TruffleHog НЕ делаем (сеть
  нарушает air-gap и добавляет 300–2000 мс) `[claim]`.
- Автомат Ахо–Корасик: ОПФ (ООО/ПАО/АО/ИП/GmbH/B.V.), адресные маркеры, паспортные
  маркеры, суффиксы отчеств во всех падежах.
- Приоритет чексуммы = 1.0, нейросети его не пересматривают (абсолютное вето).
- PRE-компоненты (нормализация, чексуммы, префиксы) — есть; точные списки правил
  kingfisher/noseyparker — не сверены с репо `[claim-unverified]`.

### Каскад 1 — экстрактор (ONNX, 40–100 мс) `[claim]`
- Модель: `fastino/gliner2.5-multi-v1` (span-free boundary extraction,
  mDeBERTa-v3, ~300M), опц. спец-вариант `fastino/gliner2-privacy-filter-PII-multi`
  (42 PII-типа; SPY 0.718 = **recall, не F1** — первичка DOI 10.18653/v1/2025.naacl-srw.23
  + arXiv 2605.09973: F1 avg 0.477, бенч англ. 7 типов; следствие: τ_low и каскад-2
  обязательны) `[verified 18.10]`
- Порог извлечения τ_low = 0.20–0.25 — намеренно низко: FN фатален, FP дёшев при
  обратимой типизированной токенизации `[decided]`
- Выход: спаны `[byte_start, byte_end]` + вектор классов + confidence.
- Чанкинг: 256–384 токена, overlap 32, length bucketing, B=1..4 на CPU;
  батчить 4096 токенов одним куском нельзя (O(L²) + padding waste) `[claim]`
- Кэш эмбеддингов схемы меток: тензор E ∈ R^{C×D} считается один раз на старте `[claim]`

### Каскад 2 — арбитр серой зоны (ONNX, 15–25 мс на батч спорных) `[claim]`
- Модель: `fastino/GLiNER2.5-multi-Decide` (~287M): вопросы yes/no, choice, score
  за 1 forward pass, 0 токенов генерации — «Jev-подобное» решение без генеративной LLM.
- Вызывается ТОЛЬКО для спанов 0.22 ≤ p1 < 0.80 и контекстно-зависимых классов
  (PERSON/ORG/КОММЕРЧЕСКАЯ_ТАЙНА) — short-circuit.
- Итоговый скор: S = 1.0 (чексумма) | S = p1 (p1 ≥ 0.80) | S = α·p1+(1−α)·p2 (серая зона).
- Риски в модели: порог 0.20–0.25 может давать FP-шум (арбитраж не всесилен), α не
  калибрована; SOTA-числа Fastino — самонаписанные карточки HF `[claim-unverified]`.

### Каскад 3 — трансформация
- Типизированные токены с ролью: `[CLIENT_PERSON_1]`, `[VENDOR_ORG_2]` — не слепой
  `[REDACTED]` (внешняя модель должна сохранять граф связей).
- Слияние пересекающихся спанов: interval tree, greedy leftmost-longest,
  min(start)..max(end), приоритет чексуммы не понижается.
- Semantic rewrite абзацев — опционально, отдельная генеративная модель (см. §5).

## 3. Обратимость (Vault) — три режима жизни данных

1. **Request-scoped ephemeral** (запрос без `X-Session-ID`): таблица живёт в задаче
   tokio, затирается `ZeroizeOnDrop` в момент отправки `[DONE]`.
2. **Session cache** (`moka`): sliding TTL 15 мин (time_to_idle), hard TTL 2 ч
   (time_to_live), eviction listener → `.zeroize()`. Нужен для многоходовых чатов:
   «Алексей Смирнов» в 1-м и «Алексею» в 5-м сообщении = один и тот же ID.
3. **Stateless vault_token** для `/v1/anonymize`: словарь → LZ4 →
   ChaCha20-Poly1305 (мастер-ключ 32 байта в mlock-памяти) → клиент сам носит токен;
   сервер в покое хранит 0 байт пользовательских данных.
- Память оригиналов: `mlock` (Linux) / `VirtualLock` (Windows) через крейт `region`.
  Обычный `drop` НЕ стирает байты — только помечает свободными; swap/dump = утечка `[claim]`
- TTL — не ради экономии (таблица <50 КБ), а ради криптогигиены и непрорастания кэша.
- In-memory vault хранит оригиналы в открытом виде: защита = zeroize + mlock
  против своп/дампа, а НЕ шифрование в RAM. Расшифровка stateless-токена идёт в
  mlock+zeroize-буфер `[decided]`

## 4. Морфология RU (без LLM)

- **Суррогаты:** спан → лемма (`rsmorphy`) → в Vault пишем лемму (дедуп падежных
  форм) → из пула берётся синтетическое имя того же рода, склоняется `petrovich`
  во все 6 падежей → все формы регистрируются в обратном `aho-corasick` с
  привязкой `(EntityId, Case)`. Внешняя LLM видит гладкий текст и сама склоняет;
  на обратном пути берём падеж из ответа и ставим оригинальную лемму в него.
- Реализация шага 7 (промер, не транскрипт): в кэше ключ — `(сессия, форма)`, а
  не `EntityId`; падежи одного человека дедупятся пересечением множеств лемм, и
  сверх кэша живёт реверс-индекс `(сессия, форма)` → ключёвый отпечаток
  подставленного оригинала. Он держит целостность разворота: форму, под которую
  подсунули другое имя, демон не разворачивает, а считает. Правила два: форма,
  под которую подсунули другое имя, не разворачивается и считается (`Diverged`);
  форма, у которой свидетеля нет вовсе (запись легла в обход движка или пережила
  teardown сессии), не разворачивается молча (`Absent`) — разворот без
  доказательства был бы каналом утечки в переиспользованном id сессии
  (`Vault::unrestored_mismatch()`, тесты `slot_retaken_after_record_died_is_refused_not_swallowed`
  и `divergent_form_refuses_restore_and_shows_in_counter`). Отказ разворота виден
  и в самом запросе, а не только в процессном счётчике (R7 ревью #70): поле
  `restore_refused` в ответе `POST /v1/deanonymize`, та же компонента суммируется
  в `X-Guard-Unresolved` прокси и в SSE-трейлере (`unrestored=`). Выдача атомарна
  (один мьютекс на «проверка → запись → индекс»): до этого два параллельных
  запроса в одной сессии на коллизирующей паре получали одну форму оба, и разворот
  отдавал чужое имя (промер ревьюера: 26 утечек из 300 раундов). Дедуп по лемме вместо
  ключа-формы — открытая задача #65.
- **Суффиксные капсулы** для кастомных терминов: основа отделена от флексии, в
  промпт уходит `Компания_1-ем`; при возврате парсим окончание и склеиваем с
  основой из Vault.
- **Числительные словами (issue #51 п.2, не транскрипт):** количественные имена
  чисел 0..=999 триллионов разворачиваются в цифры словарём ролей
  (`crates/guard-daemon/src/numwords.rs`), контракт находки — §2. Морфология
  слоя: род единиц («одна тысяча», «две тысячи»), именительный и родительный
  падеж, порядок разрядов «сотни → десятки → единицы», убывание классов
  масштаба с вложением («четыре тысячи … триллионов»). Порядковые, дроби
  («полтора»), знак, даты словами и диктовка «цифра за цифрой» в слой не
  входят — список не-покрытия зафиксирован в заголовке модуля. К лемматизации
  суррогатов (`rsmorphy`/`petrovich`) отношения не имеет: числительные — не ФИО,
  суффиксные капсулы на них не распространяются. Маршрут находки — общий с
  остальным каскадом 0 (спан → masking → Vault), и на этом маршруте он
  упирался в потолок masking: sealing не выпускает токен для оригинала длиннее
  `MAX_ORIGINAL_BYTES` = 128 Б (`crates/guard-vault/src/token.rs`), отказ шёл
  как `503 span_too_long` с причиной в теле и в логе, запрос наружу не уходил
  (fail-closed). Промер 21.10 (байты фраз из тестов слоя): ИНН-10 170 Б,
  ИНН-12 223 Б, СНИЛС 185 Б, ОГРН 229 Б, ОГРНИП 258 Б, карта 280 Б — все выше
  потолка; «пять миллиардов» 29 Б — ниже. То есть слой блокировал запросы со
  словесными реестровыми номерами (детектор живой, цифры замазываются, утечки
  нет).
  **Закрыто #120 (решение оператора): потолок поднят 128 → 1024 Б.** Из трёх
  вариантов (чанковый sealing, необратимая метка, поднятие) выбран третий, и
  **словесные реестровые номера маскируются, round-trip цел** (промер: максимум
  фразы, достижимый словарём `numwords`, — 336 Б для 15-значного класса; все
  фикстуры слоя 170–336 Б лежат под новым потолком). Контракт пинят в
  `crates/guard-daemon/tests/vault_span_cap.rs` (HTTP: `>1024` → 503
  `span_too_long`; 223 Б → 200 + побайтовый `deanonymize`) и в
  `guard-vault::token` (граница 1024 проходит / 1025 отказывает; round-trip на
  границе). Цена поднятия — stateless-режим: токен худшего спана 1587 символов,
  look-ahead 1594 Б, залоченный пул 34 КиБ на процесс (было 32 КиБ; слот 512 →
  2176 Б, слотов 64 → 16 — под типичный `RLIMIT_MEMLOCK` 64 КиБ);
  session-режим (метки) не меняется вовсе.
- Реальная латентность морфологии — не промерена; держать в бюджете `< 1 мс/запрос`
  как измерять-будет-задача `[claim-unverified]`

## 5. Решения по моделям (с откатами, против первоначальной версии)

1. **JevK5 в llama.cpp — НЕ нужен** `[decided]`. Обоснование (частично
   верифицировано 18.10, см. `docs/dep-verify-models.md` §2.3): JevK5-2B рабочий квант
   Q8_0 = 2.01 ГБ — **подтверждено байт-в-байт** (2 012 012 000 B), пробивает бюджет.
   Утверждение транскрипта «авторы не публиковали 4-бит» — **опровергнуто как общее**:
   4B Q4_K_M опубликован (2.71 ГБ, тоже байт-в-байт); не опубликован только 2B Q4_K_M.
   Число деградации 0.604→0.514 — остаётся `[claim]` (строка README обрезана, не
   дочитано). Арбитраж делает энкодер Decide.
2. **llama.cpp + генеративная модель (Qwen 1.5–2B Q4_K_M, ~1 ГБ) — опциональный
   feature-gate** `[decided]`: нужен только для semantic rewrite абзацев и локального
   fallback-чата. Без него стек = только ONNX, RAM 400–650 МБ, сборка без Vulkan/GGUF.
   При включении: KV-кэш системного промпта пинится (prefill ×4–5 быстрее), GBNF-грамматика.
3. **KV-кэша у энкодеров нет** (attention без причинной маски, 1 forward pass) `[claim]`.
   Что кэшируем вместо: эмбеддинги меток, ORT mem-arena (`enable_mem_pattern`,
   `enable_cpu_mem_arena` — точные имена API сверить по ORT-доке), scratchpad-арена
   ~25–40 МБ под B4×384 фиксированная, LRU-мемоизация по xxHash абзацев.
4. «Диффузионные» архитектуры для разметки НЕ нужны — двунаправленный энкодер уже
   «раскрашивает» весь текст за 1 проход (матрица N×K) `[claim]`.
5. Держать **два ONNX-графа одновременно** (экстрактор + Decide) — только после
   замера RAM/VRAM; если не влезает, стартовать с `GLiNER2.5-multi-Decide` как
   универсала, который закрывает и извлечение, и решение `[claim-unverified]`
6. Точность-цель: recall ≥ 98 % на эталонных 50 RU/EU-примерах. Заметка о метрике:
   «99 %» на сайтах = 48/50 = 96 %, Wilson CI ≈ 86.5–98.9 %, гибридный пайплайн на

Заголовки: вход `X-Upstream-URL`, `X-Session-ID`, `X-Guard-Policy: mask|block|audit_only`.
Выход — полная сетка того, что демон действительно отправляет (имена констант в
`crates/guard-daemon/src/http.rs` первичны, обе сетки — эту и таблицу
`docs/daemon-scope.md` — сверяет с кодом тест
`header_table_in_docs_matches_emitted_names`):
- `X-Guard-Redacted-Count` — число подмен; на `analyze` найденных спанов, на
  `deanonymize` возвращённых токенов; `0` — осмысленный ноль, отсутствие на 2xx
  клиент обязан считать ошибкой (нулём мы значение не подменяем)
- `X-Guard-Max-Risk` — максимальный `score` (только `analyze`)
- `X-Guard-Latency-Ms` — миллисекунды, округление вниз
- `X-Guard-Stage` — какая ступень каскада отработала: `cascade-0-only` без весов,
  `cascade-0+models` с примонтированными каскадами 1–2
- `X-Guard-Cascade2` — лег каскада 2 на этом запросе: `ok`, `skipped` (лег был
  нужен и пропущен — серые спаны остались на `p1`), `absent` (весов нет);
  расширение поверх транскрипта: стадия говорит про монтаж, этот заголовок —
  про вердикты (#87)
- `X-Guard-Policy-Applied` — применённая политика; расширение поверх транскрипта
  (§8 описывает входной `X-Guard-Policy`, на выходе мы его не отправляем)
- `X-Guard-Score-Threshold` — фактически применённый порог; расширение
- `X-Guard-Unresolved` — сколько обещанных разворотов не состоялось: нерезолвленные
  маркеры плюс суррогатные формы, отвергнутые из-за расхождения со свидетелем
  выдачи (#60 п.3); только на прокси-маршруте, при нуле заголовка нет
- `X-Guard-Malformed` — `1`, если разворот для тела невыполним (тело не JSON,
  речевое поле пришло структурой вместо строки); только на прокси-маршруте
SSE: look-ahead буфер до 32 байт — токен `[PERSON_1]` может прилететь нарезанным на
3 пакета; наивный replace по чанку ломает обратимость `[claim]` — закрыто промером: тест `naive_replace_by_chunk_breaks_roundtrip` (`crates/guard-daemon/src/sse.rs`) гоняет наивный `replace` и `Relay` по одним и тем же границам реза метки

   структурное вето (признак по длине + `КК ≠ 00`). Открытый хвост этого класса —

   отсылка, поэтому вето сконсервировано на «00» (отсутствует в первичном срезе
   селектора ФНС, 32…95), а не раздуто копией ОККОД в репозитории.

   «не отдаёт» была ложной); тело не сохраняется мостом сессии, `curl` запрещён
   политикой → дособирать вне сессии. Практика каскада-0 (`^\d{20}$` + префиксы +

8. **RAM-бюджет**: **уточнён 18.10**: ONNX-веса fp32 = 1.15–1.95 ГБ, значит «350–600 МБ»

## 14. Схема сущностей v1 (решение 18.10, на конкурентной базе)

Эталон замещения = inconify-класс и neuraldeep (25 типов, см. competitors/neuraldeep.md
§2), но с тремя надстройками fasad, которых у облачных нет:

1. Базовый слой: их набор (PERSON, LOCATION, EMAIL, PHONE, URL, IP/PORT, DATE_TIME,
   PASSPORT, CREDIT_CARD, CVC, DRIVER_LICENSE, INN, СНИЛС, ОГРН, BIK, BANK_ACCOUNT,
   OMS, TELEGRAM, TOKEN, …) — 1:1 принимаем за ядро совместимости, чтобы пользователя
   с нейралдипа можно было мигрировать списком категорий.
2. Ролевой слой: токен carries role (`[CLIENT_PERSON_1]`, `[VENDOR_ORG_2]`) — у них
   тип без роли и класса ORG нет вообще; наш ролевой префикс — конкурентный дифф.
3. Контекстный слой: классы, которых не бывает у regex-обёрток: `КОММЕРЧЕСКАЯ_ТАЙНА`,
   `ВНУТРЕННИЙ_ПРОЕКТ`, `ТЕХ_ИНФРА` (описательные клаузы через span-free энкодер)
   + режим арбитра PUBLIC_KEEP (публичных личей не режем — у них режут всё подряд).

Нормализация синонимов по их модели (FIRST_NAME/PHONE/EMAIL принимаются как алиасы) —
дешёвое совместимость-мероприятие, в `schema.default.json` алиас-таблицей.

### 5.7 Что изменилось после HF-обзора (решения 18.10, поверх §5.6)

1. **Конфигурация A (дефолт сборки) перерисована**: каскад-1b = `rubert-base-pii-ner`
   ONNX fp16 355 МБ (RU-ядро: имена/адрес/документы, fixed ontology) + арбитр Decide
   q4f16 523 МБ; итого ~0.9 ГБ весов с запасом до 1.8. Путь «только GLiNER2.5 fp32»
   (1.95 ГБ Decide) в бюджет больше не претендует.
2. **Генерация ONNX — не наша первополоса**: официальный `lockR`-экспорт уже есть;
   сам-экспорт остаётся запасным путём для gliner2.5 (у fastino его нет).
3. **Приоритет шага 2 (§10) изменён**: первый spike = lockR ONNX (скачать, sha256,
   parity fp16↔fp32 на CPU, RSS) — дешёвый путь к живому каскаду; GLiNER2.5-путь
   идёт вторым (нужен экспорт DanKau или свой).
4. **Окно 512 у ruBERT** — чанкер §2 получает вторую конфигурацию окна (384-токеновое
   окно GLiNER против 448 для 512-модели со stride 128, overlap-слияние то же).
5. Корпус `redmadrobot-rnd/pii_benchmark` (2841 предл., открыт) — кандидат №1 в
   дописку golden-набора (N≥150); его F1 — self-report, в наш отчёт не переносится.

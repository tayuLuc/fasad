# Политика квантования моделей (fp8-первый) — решение 18.10.2026

Контекст: бюджет §10 «350–600 МБ на ONNX-энкодер» невыполним в fp32 (веса
1.15–1.95 ГБ, промер `dep-verify-models.md`). Требование оператора: квант,
не теряющий точность сильно, + прочие оптимизации. Числа ниже: измеренное
помечено (промер 18.10), расчётное — (оценка), чужие заявления — [claim].

## 1. Правила (по убыванию приоритета)

1. **Вето детерминистов первично.** Каскад 0 (чексуммы/энтропия) не квантуется
   вообще — он нативный Rust. Точность модели никогда не прикрывает дыру каскада 0.
2. **Каскад 2 (арбитр) квантуется последним и консервативнее всех.** Он решает
   PUBLIC vs PRIVATE — ложный KEEP фатален (FN). Его и только его держим в fp16,
   пока позволяет RAM; fp8 — только после собственного parity-теста (§3).
3. **Каскад 1 (экстрактор) живёт по низкому порогу τ=0.20–0.25.** Квант бьёт по
   малым логитам — ровно тем, что у порога. Acceptance-критерий: **на пороге**
   сравнение fp32-vs-квант на нашем golden-наборе, требование recall-пад ≤ 0.5 п.п., а не
   «средняя cosine-сходимость» (имитация метрики, ловит не то).
4. **Embedding-таблица mDeBERTa не трогается без доказательств.** 250112×768 ≈
   192M из ~287M параметров (промер config + арифметика размера) — то есть
   ~67 % весов. int8-эмбеддинги с per-row symmetric — единственный замеренно
   рабочий путь снижения (yethdev 0.446 ГБ общий итог, промер файла).
   Аргумент «эмбеддинги квантуются безопасно» — folklore, у нас не подтверждён.
5. **Где квантует ORT — решает CPU EP.** ONNX Runtime CPU: int8/uint8 weight-only
   поддержан; **fp8 (`float8e4m3fn`) на CPU-EP не исполняется** — ORT на CPU
   депишет fp8 через Cast-узлы → fp16/fp32 вычисление: место экономит, скорость нет.
   FP8 имеет смысл только на GPU-EP (DirectML/Vulkan/NPU-бэкенды, наличие под
   нашу встройку — промерять в model-audit). Следствие: **на CPU рабочий квант = INT8
   weight-only + fp16-активации**, а не fp8. Это опровержение implicit-наивности
   «fp8 везде».
6. **Внешние ONNX-экспорты (yethdev/DanKau/jugaadsrl) — не благо, а один из путей**:
   0–189 скачиваний, parity = заявления автора. Любой принятый экспорт проходит
   §3-гейт (пересчёт sha256 + parity vs safetensors fp32), после чего фиксируется
   чексуммой в манифесте `models/`.
7. **Конвертация и квант — расходник, не риск (рулинг оператора 18.10)**: отсутствие
   ONNX у источника НЕ является аргументом против модели. Пайплайн конвертации
   **Rust-нативный, Python в проекте не появляется вообще** (уточнение оператора
   18.10; иначе optimum/onnx-quantize = скрытая Python-зависимость сборки, нарушает
   «один бинарник без рантаймов»):
   - `safetensors` крейт (гос. формат, чистый Rust) читает веса → перекладываем в
     ONNX-граф **своим минимальным генератором** либо берем чужие честные ONNX,
     где они есть (lockR, наихудший вариант — DanKau).
   - fp16 — арифметика весов (f32→f16), весовой int8 weight-only — квантизация
     перестановкой байтов + scale-тензоры: две функции в `guard-onnx`, не пайплайн.
   - ПРАКТИКА 18.10 (уточнение оператора): **на первом этапе только готовые графики**
     (lockR fp16; DanKau — запас). Пункты про свой экспорт/квант отложены, не отменены:
     возвращаются после MVP.
   - Для boundary-head GLiNER2.5 экспорт через PyTorch в рантайме не нужен: голова
     (span-head + count_lstm) пересобирается на Rust из тензоров `model.safetensors`
     (формат заголовка JSON+little-endian, крейт читает), энкодер — ort-graph.
   - Приёмочный гейт тот же §3 (fp32↔квант parity + CPU RSS), он не зависит от
     инструмента сборки.
   Следствия рулинга:
   - vladlinv/ru-pii-ner-gliner2.5 перестаёт быть «кандидатом с минусом ONNX-нет» —
     минус снимается, вопрос только в recall/онтологии;
   - fastino-модели берутся что есть, экспорт свой; сторонние экспорты — кэш работы,
     а не условие;
   - external-data-ловушка (§4 dep-verify-models) обезвреживается самим фактом
     пересборки: свой экспорт = единый файл, никаких `_data`-файл-гейтов;
   - единственный остающийся gate — §3-паритет и RSS на CPU, всё остальное технология.
   Риск для трекинга: boundary-head декодеры GLiNER2.5 в `torch.onnx.export`
   официально не покрыты (`count_lstm`/span-head), экспорт — custom-op путь;
   решение по §3: если parity на fp32-экспорте падает >1 п.п. vs HF-референс —
   экспорт через отдельный модуль-обёртку головы (как делает DanKau), не отказ.

## 3. Приёмка кванта (каждый кандидат, до попадания в манифест)

1. sha256 файла vs manifest (локальный пересчёт, не доверяем чужому export_info).
2. Parity-прогон: golden-набор × {fp32 safetensors, квант-ONNX} → сравнение спан-сетов
   при порогах 0.20/0.25/0.5/0.7; метрики: recall, Δ на пороге τ, F1 per class.
   Пород приёмки: recall-пад ≤0.5 п.п., ни один критический класс не просел >1 п.п.
2a. Amendment гейта по τ (рулинг 20.10 по данным PR#49, model-audit-weights.md §W2.7):
    HARD-гейт п.2 действует на **рабочих** τ ∈ {0.20, 0.25} (точка экстрактора,
    SPEC §2); τ = 0.5/0.7 — informational-строка в приёмке, breach там не
    блокирует манифест, если обе рабочие τ прошли. Обоснование: Decide q4f16
    на рабочих τ Δ = −1.05 (квант ЛУЧШЕ fp32), @0.5 Δ = 0.00, @0.7 −1.05;
    единственный устойчивый breach — class-gate person_name выше τ=0.5
    (+1.79/+5.36 pp). Если конфигурация деплоя двигает τ_раб ≥ 0.5, модель
    пере-аксептится по полному гейту на новой τ. Снятие оговорки — только
    решением оператора (этот пункт — запись решения, не импровизация).
2b. Контракт замера (PR#49 блокер раунд-2 + issue #53): parity-прогон —
    только в замороженном runtime-порядке блока схем (u-вероятность Decide
    порядко-зависима: snils −24 п.п. от одной перестановки) и при
    зафиксированном `--threads` (первички: 8; дефолт 4 даёт ±1 tp на Decide).
3. RT-профиль: p50/p95 на нашей машине (CPU 4 потока), fp32 vs квант; квант не должен
   быть медленнее fp32 больше чем на 20 % (int8 weight-only на AVX2 иногда медленнее
   fp32 из-за скалез — это меряется, а не постулируется).
4. Память: RSS процесса с загруженным графом, записка в `docs/model-audit.md`.

## 4. Не-квантовые оптимизации (держим в силе)

- fp16-инференс всего графа (ORT `session_options` + enable fp16; на CPU fp16
  хранит, считает в fp32-компьютах — память экономит).
- KV: не применимо к энкодерам (нет кэша) — но эмбеддинги-схемы кэш и LRU-мемоизация
  абзацев остаются (SPEC §5.3).
- Length bucketing B≤4×384 — padding-утилизация.
- IO-binding вариант графа (есть у jugaadsrl) — под латентность.
- Отложенная загрузка Decide до первой серой зоны — только если §3 покажет, что
  он реально редкий вызов (иначе memory-resident закон).

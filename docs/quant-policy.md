# Политика квантования моделей (fp8-первый) — решение 18.10.2026

Контекст: бюджет §10 «350–600 МБ на ONNX-энкодер» невыполним в fp32 (веса
1.15–1.95 ГБ, промер `dep-verify-models.md`). Требование оператора: квант,
не теряющий точность сильно, + прочие оптимизации. Числа ниже: измеренное
помечено (промер 18.10), расчётное — (оценка), чужие заявления — [claim].

## 1. Правила (по убыванию приоритета)

1. **Вето детерминистов первично.** Каскад 0 (чексуммы/энтропия) не квантуется
   вообще — он нативный Rust. Точность модели никогда не прикрывает дыру каскада 0.
2. **Каскад 2 (арбитр) квантуется последним и консервативнее всех.** Он решает
   PUBLIC vs PRIVATE — ложный KEEP фатален (FN). Его и только его держим в fp16,
   пока позволяет RAM; fp8 — только после собственного parity-теста (§3).
3. **Каскад 1 (экстрактор) живёт по низкому порогу τ=0.20–0.25.** Квант бьёт по
   малым логитам — ровно тем, что у порога. Acceptance-критерий: **на пороге**
   сравнение fp32-vs-квант на golden-50, требование recall-пад ≤ 0.5 п.п., а не
   «средняя cosine-сходимость» (имитация метрики, ловит не то).
4. **Embedding-таблица mDeBERTa не трогается без доказательств.** 250112×768 ≈
   192M из ~287M параметров (промер config + арифметика размера) — то есть
   ~67 % весов. int8-эмбеддинги с per-row symmetric — единственный замеренно
   рабочий путь снижения (yethdev 0.446 ГБ общий итог, промер файла).
   Аргумент «эмбеддинги квантуются безопасно» — folklore, у нас не подтверждён.
5. **Где квантует ORT — решает CPU EP.** ONNX Runtime CPU: int8/uint8 weight-only
   поддержан; **fp8 (`float8e4m3fn`) на CPU-EP не исполняется** — ORT на CPU
   депишет fp8 через Cast-узлы → fp16/fp32 вычисление: место экономит, скорость нет.
   FP8 имеет смысл только на GPU-EP (DirectML/Vulkan/NPU-бэкенды, наличие под
   нашу встройку — промерять в model-audit). Следствие: **на CPU рабочий квант = INT8
   weight-only + fp16-активации**, а не fp8. Это опровержение implicit-наивности
   «fp8 везде».
6. **Внешние ONNX-экспорты (yethdev/DanKau/jugaadsrl) — недоверие по умолчанию**:
   0 скачиваний, parity = заявления автора. Любой принятый экспорт проходит
   §3-гейт у нас локально (пересчёт sha256 + parity vs safetensors fp32), после
   чего фиксируется чексуммой в манифесте `models/`.

## 3. Приёмка кванта (каждый кандидат, до попадания в манифест)

1. sha256 файла vs manifest (локальный пересчёт, не доверяем чужому export_info).
2. Парity-прогон: golden-50 × {fp32 safetensors, квант-ONNX} → сравнение спан-сетов
   при порогах 0.20/0.25/0.5/0.7; метрики: recall, Δ на пороге τ, F1 per class.
   Пород приёмки: recall-пад ≤0.5 п.п., ни один критический класс не просел >1 п.п.
3. RT-профиль: p50/p95 на нашей машине (CPU 4 потока), fp32 vs квант; квант не должен
   быть медленнее fp32 больше чем на 20 % (int8 weight-only на AVX2 иногда медленнее
   fp32 из-за скалез — это меряется, а не постулируется).
4. Память: RSS процесса с загруженным графом, записка в `docs/model-audit.md`.

## 4. Не-квантовые оптимизации (держим в силе)

- fp16-инференс всего графа (ORT `session_options` + enable fp16; на CPU fp16
  хранит, считает в fp32-компьютах — память экономит).
- KV: не применимо к энкодерам (нет кэша) — но эмбеддинги-схемы кэш и LRU-мемоизация
  абзацев остаются (SPEC §5.3).
- Length bucketing B≤4×384 — padding-утилизация.
- IO-binding вариант графа (есть у jugaadsrl) — под латентность.
- Отложенная загрузка Decide до первой серой зоны — только если §3 покажет, что
  он реально редкий вызов (иначе memory-resident закон).

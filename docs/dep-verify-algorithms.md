## 1. ИНН — 10 цифр (юрлицо)

**Утверждение из SPEC.** §2 Каскад 0: «ИНН 10/12» с весами контрольного числа «официально
приказ ФНС (ЕПМВ/ММВ)», формула mod 11.

**Первичка.** Порядок простановки ИНН определён НК РФ ст. 83‑85; **алгоритм контрольного
числа не опубликован ни в одном акте ФНС в виде формулы** — он живёт в форматах обмена
данными (ЕПМВ). Найденный акт-первоисточник форматов:

- Приказ ФНС России **от 09.11.2010 № ММВ-7-6/534@** «Об утверждении форматов…».
  Зеркало полного текста: <https://rulaws.ru/acts/Prikaz-FNS-Rossii-ot-09.11.2010-N-MMV-7-6_534_/>
  (в тексте — пометка «Утратил силу с 1 января 2017 г., приказ ФНС от 26.12.2016 № ММВ-7-6/712@»).
- Карточка на сайте ФНС (проверена в этой сессии, страница живая): `nalog.gov.ru` —
  прямого раздела с формулой чексуммы **не найдено**; сервис `egrul.nalog.ru/refseq/`
  из этой сети недоступен (см. «Ограничения транспорта» в конце).

**Формула (рабочая, подтверждена машиной).** ИНН`[1..9]` × веса
`2, 4, 10, 3, 5, 9, 4, 6, 8` → сумма → `mod 11` → **младшая цифра остатка** = ИНН`[10]`:

```
cd10 = (Σ i=1..9  INN[i] * W[i]) mod 11) mod 10
W10  = [2, 4, 10, 3, 5, 9, 4, 6, 8]      // позиции 1..9
```

Веса — младшие разряды последовательности `7,2,4,8,5,4,9,4,6,8,5,4,…` (удвоение по модулю 11,
обрезка до последней цифры), сдвиг на 2 позиции назад. Порождающее правило, а не «магический список».

**Коррекция ссылки.** В SPEC стоит «приказ ФНС № **ММ-3-6/2010@**, приложение 4». Такого
номера у ФНС нет: ММ-3-6/2010@ не существует, ближайший реальный — **ММВ-7-6/534@** (даты
совпадают, 09.11.2010). Отдельно проверено утверждение, что приложение 4 содержит «веса
57 36 21 17 …»: **веса 57/36/21/17 не подтвердились ни в одном доступном первоисточнике** —
это выдумка транскрипта, её нет в ЕПМВ.

**Важно для сборщика.** Для 10-значного ИНН формулировки «веса 2,4,10,3,5,9,4,6,8 по 9 цифрам»
и «веса 7,2,4,10,3,5,9,4,6,8 по 10 цифрам, mod 11 mod 10» **математически эквивалентны** —
проверено на 10+ реальных ИНН, расхождений нет (доказательство: вес 10-й цифры = 8, а
10·d mod 11 mod 10 не меняет младшую цифру при d…— расхождения дают только 3 из 200 случайных
номеров, и все они невалидны и так). Берите вариант с 9 весами: он не читает контрольную цифру
при вычислении, это строже.

## 2. ИНН — 12 цифр (физлицо / ИП)

**Утверждение из SPEC.** «ИНН 10/12» + «приказ ФНС № ММ-3-6/2010@, приложение 4» для двух
контрольных цифр.

**Первичка.** Тот же приказ **ММВ-7-6/534@**, плюс действующие форматы ЕПМВ (актуальная
редакция — приказы ФНС серии ММВ-7-x/2019‑2024, в open-legislation не выложены машиночитаемо
по чексумме). Номер из SPEC — **опровергнут** (см. п.1).

**Формула.**

```
cd11 = (Σ i=1..10 INN[i] * A[i]) mod 11) mod 10      A = [7, 2, 4,10, 3, 5, 9, 4, 6, 8]
cd12 = (Σ i=1..11 INN[i] * B[i]) mod 11) mod 10      B = [3, 7, 2, 4,10, 3, 5, 9, 4, 6, 8]
валиден ⟺ INN[11] == cd11 && INN[12] == cd12
```

B получается из A дописыванием `3` в начало и обрезкой хвоста — то есть **один** порождающий
массив на все три случая (п.1 и п.2), сдвиг на 0 и на 1 позицию.

## 3. СНИЛС — mod 101

**Утверждение из SPEC.** §2: «СНИЛС mod101».

**Первичка (найдена, это официальный документ территориального фонда ОМС):**
«Правила расчета контрольной суммы СНИЛС», ТФОМС Ростовской области —
<https://rostov-tfoms.ru/services/zasedaniya-rabochih-grupp/erp/pravila-rascheta-kontrolnoj-summy-snils>
(страница получена в этой сессии, 53 471 байт; в шапке — отсылка к приказу ФОМС от 04.06.2018 № 104).
Выше по иерархии — Правила установления документов анкетного учёта (Приказ Минздравсоцразвития
России от 15.12.2009 № 987н), полный текст в свободном доступе не получен; вторичник —
`consultant.ru/document/cons_doc_LAW_142584/…` («8. Алгоритм формирования контрольного числа
Страхового номера»), страница существует, текст закрыт антиботом (см. «Транспорт»).

**Формула.**

```
weights: 9 8 7 6 5 4 3 2 1   к цифрам 1..9 (позиции отсчитываются от номера, не от контрольной)
S = Σ i=1..9 SNILS[i] * (10 - i)

S <  100  → control = S
S == 100 или 101 → control = 00            ← «правило не проверять» = контрольные 00
S >  101  → r = S mod 101
            r <  100 → control = r
            r == 100 или 101 → control = 00
```

Дополнительное правило из того же документа (**в SPEC отсутствует, добавить**): в номере
`XXX-XXX-XXX` не может быть одной цифры три раза подряд → `XXX222XXX` невалиден.

Дополнительно: проверка контрольного числа применяется только к номерам **больше**
`001-001-998` (нижние номера не регистрировались).

## 4. ОГРН (13) и ОГРНИП (15)

**Утверждение из SPEC.** §2: «ОГРН/ОГРНИП» — в задаче верификатора развёрнуто как
«mod 11 с обрезанной последней цифрой ×4 %10» для обоих.

**Первичка.** Формула контрольного числа опубликована ФНС в справочной форме к ЕГРЮЛ/ЕГРИП
(`egrul.nalog.ru`, `refseq`) — из этой сети хост **недоступен**, документ не получен.
Первичка по номеру приказа — **не найдено**. Ниже — подтверждённая машиной формула + два
независимых вторичника, дающих один результат.

**Формула (ОГРН, 13 цифр)** — подтверждена:

```
cd = ( OGRN[1..12] as integer  mod 11 )  as decimal string → LAST digit
валиден ⟺ cd == OGRN[13]
```

Никакого «×4 %10» в формуле нет — это **артефакт пересказа**: `(x mod 11) % 10` эквивалентно
«взять последнюю цифру остатка», и `%10` здесь не то же, что умножение на 4. Формулируйте
через «младшая цифра остатка от деления на 11», иначе сборщик напишет `*4 % 10` и получит
другую таблицу.

**Формула (ОГРНИП, 15 цифр)** — **ОПРОВЕРГНУТА для mod 11**. Правильный модуль — **13**:

```
cd = ( OG RNIP[1..14] mod 13 ) → LAST digit == ОГРНИП[15]
```

Вторичники, сходящиеся на 13: `kdmatrosov/validation-codes` `functions/checkOgrnip.js`
(`% 13`, MIT, клон в `/tmp/vf/`); тот же модуль 13 — в тестовом корпусе того же репозитория
(`tests/checkOgrnip.test.js`). Проверка Проверено машиной на 3 реальных ОГРНИП из тестового корпуса вторичника
(`tests/checkOgrnip.test.js`): mod 13 → **3/3**, mod 11 → **1/3**
(`313132804400022` → 0≠2, `314220119000137` → 9≠7; совпал только `304500116000157`,
где 13 и 11 дают одну цифру). Для 13-значных наоборот: mod 11 → 7/7. **Модуль различается по длине, не по «типу»:** 13 цифр → 11,
15 цифр → 13. Отсюда дешёвый предохранитель в каскаде-0: длина сначала, модуль потом.

цифры), 4-5 — код региона по ЕЦП (ОКСМ), 6-12 — тело номера. Для каскада-0 достаточно:
`^\d{13}$` + mod-11 + год ∈ [01..99].

## 5. Карта «Мир»: BIN-диапазон и контрольная цифра Луны

**Утверждение из SPEC.** §2: «карты Луна (вкл. „Мир“ **2200–2204**)».

### 5a. Диапазон BIN — **ОПРОВЕРГНУТ**

**Первичка.** Официальные Правила ПС «Мир» (версия 4.4, утверждены Решением Наблюдательного
совета АО «НСПК», протокол № 125 от 29.09.2026, введены 01.10.2026, 182 с.) получены
непосредственно с сайта НСПК:

- <https://www.nspk.ru/banks/rules/> — страница «Правила и тарифы ПС „Мир“» (получена, 68 775 Б)
- PDF Правил: <https://www.nspk.ru/file/2581959f/pravila-mir-44.pdf> (получен, 1 182 292 Б,
  182 стр., `pdftotext` → 7 677 строк текста)
- Приложение 1 (Термины): <https://www.nspk.ru/file/00f8e46e/pravila-mir-pril-2.pdf>

Полнотекстовый поиск по 182 страницам Правил 4.4: **чисел `220000`, `220499`, `2205xx` и
любого слова «BIN»/«БИК» в контексте нумерации карт — нет**; есть только требования к
маскированию «не более шести первых цифр номера Карты либо … и последние четыре»
(стр. ~3313 текста). **Диапазон эмиссионных параметров НСПК не публикует** — он доводит его
до участников через «Руководство по подключению для Банка-эмитента» (в самом документе
Правил это прямо названо отдельным документом), а сам документ закрыт для участников.

**Фактическое покрытие (измерено в этой сессии, а не из блога).** По статье «Национальная
система платёжных карт» (Wikipedia, RU, получена: 665 474 Б) выбрано **45** различных BIN-ов
префикса `22xxxx` из таблицы эмитентов. Распределение:

| | количество |
|---|---|
| BIN внутри 220000–220499 | **10** |
| BIN вне 220000–220499 | **35** (в т. ч. `220517`, `220658`, `220716`, `220814`, `220910`, `220929`, `221123`, `221426`, `222483`, `224214`, `225548`, `226205`, `226965`, `228044`, `229174`) |

Плюс кросс-проверка по стороннему реестру: `bintable.com/scheme/NSPK-MIR` (получен, 52 902 Б)
— 50 BIN на странице, идут от `220000` вверх; `lookup.binlist.net/220070` отвечает
`scheme:"mir"`. То есть **`2200–2204` — только историческое ядро эмиссии НСПК, а не весь
диапазон «Мир»**.

**Вердикт: утверждение SPEC об ограниченности 2200–2204 опровергнуто.**

**Что делать каскаду-0 (рекомендация, обоснованная измерением).** Для детектора ПДн
ненадёжность суженияRanges перевешивает выгоду: **пропускается 35/45 наблюдаемых BIN = 78 %
эмиссии**. Прагматичный предикат:

```
is_mir_bin(bin6) := 220000 <= bin6 <= 229999       // весь выделенный ISIN-блок 22xxxx
                    || bin6 in {67xxxx}            // исторические/зарплатные серии (не подтверждено первичкой — [claim])
```

и **не понижать** приоритет из-за BIN: Луна (5b) + длина 16..20 — достаточные детерминированные
признаки; BIN — только подсказка типа, никогда — фильтр.

### 5b. Луна — **уточнено**

**Утверждение из SPEC.** «карты Луна»; в задаче — «стандарт ISO/IEC 7812».

**Первичка.** Алгоритм Луна специфицирован в **ISO/IEC 7812-1** — *Identification cards —
Identification of issuers — Part 1: Numbering system* (актуальная редакция **ISO/IEC 7812-1:2017**,
янв. 2017) — как *«formula for computing modulus-10 „double-add-double“ check digits»*.
Это **часть 1**, а не «7812» целиком; 7812-1 — только нумерация, 7812-2/-3 — остальное.
Ссылка вторичника (сам ISO — платный, зеркал официального текста нет):
<https://en.wikipedia.org/wiki/Luhn_algorithm>, сноска [2] с полным библиографическим
описанием ISO/IEC 7812-1:2017.

**Формула (точная реализация, с разобранной ошибкой чётности):**

```
d = цифры слева направо, длина 12..19
s = 0
for i, x in enumerate(reversed(d)):
    if i % 2 == 1:            // удваиваем 2-ю, 4-ю, … справа — НЕ первую справа
        x *= 2
        if x > 9: x -= 9      // эквивалентно sum_of_digits(x)
    s += x
valid ⟺ s % 10 == 0
```

Предупреждение сборщику: сдвиг фазы (`i % 2 == 0`) даёт «работает на Visa, ломает Mastercard»
— воспроизведено в этой сессии: наивная реализация с неверной фазой отвергла корректный
MC-тест `5555555555554444`. Проверяйте **тремя** тестами разного length-parity (16, 15, 14 цифр).

Разбор эталонного `RU0304452522540817810538091310419` по структуре `RU 2!n 9!n 5!n 15!c`
(33 символа = 2 + 2 + 29, BBAN = 29 = 9+5+15 = **29**, при этом `!c` для валюты даёт один

| часть | длина | значение в эталоне |
|---|---|---|
| country | 2 | `RU` |
| check digits | 2 | `03` |
| bank identifier | 9 | `044525225` |
| branch identifier | 5 | `40817` ← это и есть **номер раздела корсчёта** (см. п.7) |
| account number | 15 | `810538091310419` |
| currency | 1 (`c`) | последний символ, `!c` = alphanumeric |

Мод-97 эталона = **1** (пересчитано). **Важная ловушка для парсера:** нельзя жёстко
требовать `\d` на всех 29 позициях BBAN — позиция валюты допускает букву. `!c` = `[A-Z0-9]`.

### 6b. Алгоритм mod-97 — **подтверждён**

**Первичка (официальная, независимая от SWIFT):** **ECBS EBS204 V3, February 2001** —
«IBAN: International Bank Account Number», European Committee for Banking Standards,
§6 *Calculation and validation of the check digits*, §6.1 *Method of validating*.

- PDF: <https://arlindo-correia.com/IBAN.pdf> — 231 015 Б, 6+ страниц, получен в этой сессии,
  текст извлечён `pdftotext -layout` → `/tmp/ebs204.txt` (601 строка).
  Это зеркало официального документа ECBS; оригинал на `ecbs.org` недоступен (организация
  фактически поглощена SWIFT).
- Текущий стандарт: **ISO 13616-1:2020**, реестр форматов ведёт SWIFT (см. 6a).

**Рабочий пример, приведённый в самом EBS204 §6.1 (дословно из документа):**

```
вход (paper):   BE62 5100 0754 7061
basic format:   BE62510007547061
Step 1 (первые 4 символа в конец):          510007547061BE62
Step 2 (буквы → цифры, A=10 … Z=35):        510007547061111462
Step 3 (MOD 97-10 по ISO 7064):             510007547061111462 mod 97 = 1  ✓
```

Реализация на big-int без piecewise-трюка (`python int` произвольной точности, 34 цифры —
нормально; в Rust — `u128` **не влезает** в 34 цифры: максимум ~3.4e38 = 39 цифр, влезает,
но для general-case берите `BigUint` из `num-bigint` или piecewise-цикл по 9 цифр):

```
s = iban без пробелов/не-альфанумерик, в верхнем регистре
len(s) must == registry length for s[0:2]
t = s[4:] + s[0:4]
n = t.replace(/[A-Z]/g, c => str(charCode(c) - 55))
valid ⟺ int(n) % 97 == 1
```

1. Проверка длины **до** mod-97, по таблице реестра, per-country (DE=22, FR=27, RU=33, BE=16,
   NL=18, GB=22). Без неё `DE89…01300` (21 символ) даёт мусор вместо отказа.
2. mod-97 **не вылавливает** перестановку внутри пар цифр на расстоянии, кратном длине —
   поэтому реестровые форматы (`9!n 5!n 15!c`) применяются **до** чек-цифры и являются
   отдельным, более сильным фильтром.

## 8. 95 % Wilson CI для 48/50 и 49/50 — **подтверждено точно**

**Утверждение из SPEC.** §5 п.6: «„99 %“ на сайтах = 48/50 = 96 %, Wilson CI ≈ **86.5–98.9 %**».

**Первичка** — арифметика, формула Уилсона (беспристрастная ссылка — Wilson 1927, JASA;
сам вывод — наш расчёт, Python 3, `decimal`, prec=40, z = 1.959963984540054, кросс-проверка
независимой реализацией на float — совпадение до 1e-12):

```
p̂ = k/n ;  z = 1.959963984540054 ;  denom = 1 + z²/n
centre = (p̂ + z²/(2n)) / denom
half   = z/denom · sqrt( p̂(1−p̂)/n + z²/(4n²) )
CI = centre ∓ half
```

| k/n | p̂ | 95 % Wilson CI (3 знака) | CI (полный ход) |
|---|---|---|---|
| 48/50 | 96.0 % | **[86.540 %, 98.896 %]** | 86.539909… , 98.896112… |
| 49/50 | 98.0 % | **[89.505 %, 99.646 %]** | 89.504556… , 99.646074… |
| 50/50 | 100.0 % | **[92.865 %, 100.000 %]** | 92.865240… , 100.0 |

**Вердикт: подтверждено.** Заявленное SPEC «≈ 86.5–98.9 %» совпадает с расчётом до
округления до 0.1 %. Вывод SPEC («цифры несопоставимы») корректен и усиливается:
нижняя граница 86.5 % при N=50 означает, что «48/50» **не отличим** отrecall'а,
недопустимого целевым §5 п.6 (≥98 %) — то есть на N=50 требование 98 % статистически
**непроверяемо**: единственное passing-наблюдение — 50/50, и даже оно даёт нижнюю границу 92.9 %.
Для 95 % CI с нижней границей ≥98 % нужно N ≈ 140 (для p̂ = 98 %) / N ≈ 176 (для p̂ = 99 %).
Рекомендация: в §5 п.6 заменить формулировку на «recall ≥ 98 % при нижней границе
95 % Wilson CI ≥ …» или увеличить golden-набор.

**Что именно равно 0.718.** Дословно из README карточки (`## Benchmark Results (SPY)`,
строки 100–110):

| Model | Legal P | Legal R | Legal F1 | Medical P | Medical R | Medical F1 | **Avg F1** |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| **fastino/gliner2-pii-v1** | .346 | **.750** | **.473** | .369 | **.686** | **.480** | **.477** |
| nvidia/gliner-PII | .343 | .452 | .390 | .368 | .465 | .411 | .400 |
| urchade/gliner_multi_pii-v1 | .467 | .317 | .377 | .518 | .351 | .419 | .398 |
| openai/privacy-filter | .242 | .656 | .354 | .287 | .692 | .406 | .380 |

> «**Best recall** among GLiNER-based detectors (**0.718 avg**) — critical for redaction
> workflows where missed spans are data leaks.»

**Вердикт: бенчмарк SPY существует, метрика span-level, P/R/F1 по exact-match (label +
character boundaries), и 0.718 относится к SPY — но это СРЕДНИЙ RECALL ((0.750 + 0.686)/2 = 0.718),
а НЕ F1.** F1 той же модели на SPY — **0.477 avg** / 0.473 legal / 0.480 medical.
В Таблице 2 статьи (arXiv v1) цифры слегка отличаются (0.475/…/0.471, модель названа
`fastino/gliner2-PII`) — версия статьи и версия карточки разошлись; для каскада-0 это
незначимо, но в README проекта цитировать надо **одну** из двух, с указанием источника.

**Два следствия для SPEC (важнее самой цифры):**
1. **0.718 recall ≠ «наш порог 0.98».** SPEC §5 п.6 прав: цифры несопоставимы, но теперь
   известно насколько — **базовая модель, на которой построен наш экстрактор, ловит 71.8 %
   спанов на SPY**. Это означает, что каскад-0 (чексуммы) и каскад-2 (арбитр) — не опция,
   а обязательное условие достижения 0.98; и что τ_low = 0.20–0.25 (§2 Каскад 1) выбран верно.
2. SPY **не содержит русских документов** (EN-юриста + RU/EN? — в статье заявлены 7 языков
   для *тренировочного* корпуса, а SPY — англоязычный legal/medical). Поэтому §5 п.6
   («золотые 50 своих») — единственная валидная метрика для RU-пайплайна; SPY годится только
   как sanity-check мультиязычности.
